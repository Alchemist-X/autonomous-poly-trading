# 预测引擎 PRD — Forecasting Engine：活报告控制台（Living Forecast Console）

> 状态：草案 v0.1 · 2026-06-21 · 作者：Claude（基于现有 `/research` + Pulse/forecast 代码实测，非凭空设计）
> 定位：把现有 `/research`（Forecasting Engine）从"跑完即弃的一次性流"升级为"边长边能对话的活报告"。**通用预测引擎，不止世界杯**。
> 英文副本：`2026-06-21-prediction-engine-prd.en.md`（**待同步翻译** — 中文为准）。
> 来源：本 PRD 由一次多 agent 工作流产出（7 路并行读码理解现状 → 3 套 UX 设计视角 + 后端架构 → 综合 → 可行性审查 → 15 章起草 → 完整性审查）。第 0 节"口径统一"是审查后由主笔收口的权威决定。

## 一句话

把一次 12–15 分钟的预测，做成一份"边长边能对话"的活报告：左边实时活动流让你看着它推理、随时插话，右边是一份会自我更新的结论文档；引擎不停、断网能重连、你说的话在下一个安全检查点被采纳并明确回流。

## 结论先行（给 PM 的三句话）

你最关心的三件事，对应到落地难度（已对现有代码核实，不画饼）：

- **① 动态过程展示**（怎么让 12–15 分钟不像死机）：现有 7 阶段 SSE 流 + 纯 reducer 已做完 **80–90%**。只需两件小事：把"跑完即弃"改成"常驻活报告"，再补**心跳**——每 10–15 秒一帧，把"静默 5 分钟"翻译成会动的"仍在【称重证据】阶段 · 已 8m12s · 该阶段约 2–4min"。诚实底线：心跳是改善体感，不是给慢引擎打掩护，渲染持续 >15min 仍按性能回归处理。
- **② 加 context**（怎么让用户运行中自主加料）：改动最大的一项，统一走 **旁路 POST + 阶段边界采纳**（**绝不上 WebSocket**）。你随时插话 → 乐观回显"你说了…" → 引擎在下一个 stage 边界读取待处理队列 → 采纳后发 `context.applied` 明确回流 + 显示概率怎么变。分三档：轻档（贴链接/粘文本当背景或证据）、中档（否决/锁定某条证据，前端秒级重算、0 token）、重档（改判定参数如换截止日，局部重跑受影响节点）。
- **③ 交互**（报告从只读升级为可对话）：分两层、按风险递增上线。**第一层**（纯前端、先上、性价比最高）：每条证据可忽略/降权/提权 → 本地秒级重算最终概率与可信区间；节点/来源/局限全部可展开折叠；来源 url 渲染成可点链接。**第二层**（需引擎配合、第二步）：局部重算（只重跑受影响的节点及下游，而非整轮 12–15min）+ 追问（生成继承父 run 证据池的子 run，省 token）。

## 一个架构决策撑起全部

最核心的改动：把**同步流式**改成**异步 run + 可重连流**。现在整条流挂在一个 POST 的生命周期上——用户切后台 / 网络抖一下 / CDN 超时，整段就丢且无法恢复，这对 12–15min 长任务是致命的。改成：

```
POST /api/research/runs            → 秒回 { runId, status: "queued" }   （不阻塞 12–15min）
GET  /api/research/runs/{id}/stream → 独立订阅 SSE（断线靠 Last-Event-ID 续传，不重放整段）
GET  /api/research/runs/{id}        → 拉快照（刷新 / 历史回看 / 分享）
```

这一步**一次性**解决四件事：长任务断网恢复、运行中加 context（另一请求要能读写同一 run 的 store）、刷新/历史、分享。SSE 协议本身不变（仍是 `ResearchEvent` 判别联合），只给每帧加 `id:` 序号支持续传 + 新增 4 类事件，前端 reducer 近乎零改、`default` 分支天然向后兼容老 driver。

## 0. 口径统一（权威修订 — 与个别章节正文冲突处，以本节为准）

完整性审查（对照真实代码逐条核验）发现 15 章草稿里有若干口径漂移。下面是收口后的权威决定，**正文如有出入以此为准**，落库/实现按此执行：

1. **i18n 用对文件、只两语**：`/research` 控制台用 `apps/web/lib/research/i18n.ts`，`locale.ts` 写死 `ConsoleLocale = 'en' | 'zh'`——**只有 en/zh**，**不是** 世界杯那套 `apps/web/lib/world-cup/messages/` 的三语（en/zh-CN/zh-TW）。文中个别章节误写"三语 / zh-TW"，以本条为准。若决定扩 zh-TW，需先改 `ConsoleLocale` 类型，记 P2。
2. **followup（追问）= 独立子 run**：继承父 run 的证据池、带 `parentRunId` 指针。父 run 上的 `followups[]` 只是反范式索引（给 UI 快速列出），**数据归属以独立子 `PredictionEngineRun` 实体为准**。§8 数据契约据此落库，不要把它当成父 run 的内联记录。
3. **版本（version）有契约支撑**：报告冻结成版本需在 §8 补 `versions[]`，每版 `{ versionId, atSeq, yesProbability, conclusionSnapshot, triggeredBy }`；版本对比（v1 22% → v2 28%）的 diff **基于 `versions[]`**，不靠 `contextLog` 反推。
4. **心跳统一用 `run.heartbeat`**：不再"stage.heartbeat / run.heartbeat 二选一"。reducer 只处理一种，UI"仍在工作"指示器以 `run.heartbeat` 为准（帧内带 `currentStageId / elapsedMs / stageEtaMs`）。
5. **VPS 超时目标 ≥18min**：当前 VPS 端 120s 超时与 12–15min 渲染直接冲突，统一改到 **≥18 分钟**（引擎内部 `claude --print` timeout 保持 30min），并写进 §7.3 长任务架构与 §13 里程碑的验收标准。
6. **cost-ledger 目录首次运行时创建**：`runtime-artifacts/pulse-live-cost-ledger/` 当前**不存在**（`runtime-artifacts/` 下目前只有 `world-cup/`），按成本画像约定**首次 live run 时创建**，非错误。§9/§11/§12/§15 引用它时按"首次运行创建"理解。
7. **`idempotencyKey` 语义**：`POST /runs` 请求体的幂等键——同一 key 在 TTL（建议 10min）内重复提交 / 断网重试，**返回同一 `runId`、不重复起 run**。是异步化后防重复计费/重复跑的必需项。
8. **queued→accepted 空窗体验**：异步排队期（数秒~数十秒）UI 显示"排队中…"骨架占位；`run.accepted` 事件携带 `stages[]` 后，右栏再铺 7 阶段空位骨架。不要让用户在 queued 阶段看空白。

## 1. 概述与定位

> 本节回答四件事：这是什么、给谁用、凭什么有人用、和现在线上那个 `/research` 是什么关系。不展开实现，实现细节见后续各节。

### 1.1 一句话定义

**Forecasting Engine 是一个通用的"活报告"预测控制台**：你用一句自然语言问一个可验证的二元问题（"X 会不会在某日期前发生"），它在 12–15 分钟里一边推理一边把一份会自我更新的结论文档"长"给你看——左边是实时活动流（看着它推理、随时插话），右边是一份随证据收敛的活报告（结论概率、条件概率树、贝叶斯瀑布、可点开的证据台账）。引擎不停、断网能重连、你说的话在下一个安全检查点被采纳并明确回流。

和今天 `/research` 最大的区别只有一句话：**从"跑完才弹出的静态报告"升级成"边长边能对话的活报告"**。

### 1.2 目标用户

按优先级排序，不是平铺：

| 用户 | 他们要解决什么 | 这个产品给他们什么 |
| --- | --- | --- |
| **想对某个具体事件下判断的决策者**（投资/政策/赛事/商业事件） | "这事到底多大概率发生，依据是什么，我信不信得过" | 一个带概率 + 80% 可信区间 + 可审计证据链的结论，而不是一段没法核对的文字 |
| **要审证据、要反驳的专业读者** | "这个数字是怎么算出来的，哪条证据在拉高/拉低，我不认可某条能不能去掉" | 可点开每条证据看原文、可"忽略此条"即时重算、可对节点追问的可交互报告 |
| **预测产品的运营/评测方**（含世界杯盲测团队） | "把一次预测留档、事后和市场对比打分" | 结构化、可归档、可回放的 run（`PredictionEngineRun`），事后基准评测复用同一套数据 |

**不是给谁用**：这不是交易执行界面。它只产出"概率 + 依据"，不下单、不碰钱包、不读市场价来形成预测（盲测边界见 1.5）。交易侧是 `scripts/pulse-live.ts` / `services/orchestrator` 那条真钱链路，两者共用推理引擎但产品形态完全分开。

### 1.3 价值主张

一句话结论：**市面上大多数"AI 预测"给你一个数字和一段话，你没法核对、没法干预、跑起来像死机；我们给你一份能看着它推理、能当场质疑、能断网重连的活报告。**

拆成三个能被验收的具体承诺：

1. **可审计**——每条证据是一个四元组（立场 / 影响 ±pp / 信度 0–1 / 挂在哪个条件节点），明确绑定到"这条新闻把 A 节点概率拉高了几个点"。这是整份报告的最小可信单元，对应 `apps/web/lib/prediction-engine-demo.ts` 里的 `PredictionEvidence`（`stance` / `weightPct` / `reliability` / `node`），不是事后编的展示字段。
2. **可干预**——运行中能往里加背景/贴链接当证据/否决某条证据；纯前端的"忽略某条证据"秒级 0-token 重算当场看概率怎么变，需要引擎配合的"加新料局部重算"作为第二步。今天的 `/research` 是单向直播，只能看不能说。
3. **不假死、不丢**——长任务每 10–15 秒发一帧心跳（当前在干嘛 + 已耗时 + 预计区间），把"静默 5 分钟"（实测正常）翻译成会动的"仍在工作"；断网/刷新能从断点续传，不像现在一断全丢。

诚实边界，先说在前面：心跳是改善体感，不是给慢引擎打掩护——渲染持续 >15 分钟仍按 regression 处理（依据 `docs/diagrams/forecasting-cost-profile.md` 实测：一轮 ≈ 12–15 分钟、约 40–50k 输入 / 5k 输出 token、渲染占 95%）。

### 1.4 与现有 `/research`（Forecasting Engine）的关系

**结论：不是另起炉灶，是对线上 `/research` 控制台的增量升级——复用其展示层与纯 reducer，新增长任务承载、反向通道、可交互层。**

现状盘点（哪些已就绪、哪些是真缺口）：

| 现有资产（直接复用） | 位置 | 复用程度 |
| --- | --- | --- |
| 7 阶段 SSE 事件流 + 11 种事件协议 | `apps/web/lib/research/events.ts` | 协议不变，仅新增 4–6 类事件 |
| 纯 reducer（`default` 分支天然向后兼容未知事件） | `apps/web/lib/research/state-machine.ts` | 几乎零改 |
| 5 张结果卡（结论卡 / 条件树 / 瀑布 / 证据台账 / 局限） | `apps/web/components/research/result-charts.tsx` | 叶子绘制逻辑复用，外壳与渲染时机重写 |
| 阶段时间线、状态机图例 | `apps/web/components/research/stage-timeline.tsx`、`state-machine-legend.tsx` | 复用 |
| SSE 客户端流 hook | `apps/web/lib/research/use-research-stream.ts` | 续传需扩传输层 |
| 三 driver 热切换（mock / api / vps） | `apps/web/lib/research/drivers/` | 复用，承载位置待拍板 |
| replay 引擎（结构化输出 → 定时事件流） | `apps/web/lib/research/replay.ts` | 复用 |

三个**真实缺口**（本 PRD 要补的）：

1. **单向流不能重连**——整条流挂在一个 POST 的生命周期上，切后台/网络抖一下就全丢，对 12–15 分钟长任务是致命的。
2. **不能加 context**——运行中用户说不上话，没有上行链路。
3. **结果卡只读**——证据台账不能点开看原文、不能"忽略此条"、节点 rationale 不能展开。

> ⚠️ **重要前提（需在后续"长任务架构"节深入，此处先标红）**：当前 `/research` 生产部署在 Vercel Serverless（`apps/web/app/api/research/stream/route.ts` 的 `runtime = "nodejs"`，`vercel.json` 未配 `maxDuration`），单函数有墙钟硬上限，**现有 12–15 分钟的真 run 在 Vercel 上跑不完**——线上三条 driver 里只有 mock（约 12 秒）能跑完整、VPS driver 还卡在 120s 超时（`apps/web/lib/research/drivers/vps-agent-driver.ts`）。也就是说 C 端 `/research` 至今**没真正跑过一次 12–15 分钟的真 run**。这意味着"异步化 + 长任务承载"不是小增量，而是前置阻塞决策；本节先锁定产品形态，承载方案与取舍留到长任务架构节。

**命名澄清**：C 端 `/research` 控制台已对外品牌化为 "Forecasting Engine"（旧称 "Deep Research"）。本 PRD 标题里的"预测引擎 / Forecasting Engine"指的就是这个升级后的活报告控制台，不是 `services/orchestrator` 里的 Pulse 交易引擎——两者共用 7 阶段推理结构，但 Pulse 是 CLI 批处理、面向真钱交易，`/research` 是 C 端只读/可对话产品。

### 1.5 范围：通用预测引擎，不止世界杯

**结论：这是一个通用的二元事件预测引擎，世界杯只是当前最成熟的一个用例，不是产品边界。**

- **通用形态**：任何"可验证的二元未来问题"都能进——核协议、议息、监管裁定、商业里程碑、体育赛果。输入是一句自然语言 + 可选截止日，输出是同一套 `PredictionEngineRun` 结构（7 阶段：理清定义 → 基础推理与 query → 证据收集 → 证据权重 → 结构化模型 → 贝叶斯更新 → 结论与市场对比）。现有 `apps/web/lib/research/sample-cases.ts` 里的两个样例（伊朗核协议=真实 Skuld 快照、美联储降息=mock）就说明它本就不绑定单一领域。
- **世界杯的特殊地位**：世界杯是当前唯一跑过大规模盲测、且有事后评测页（`/world-cup/performance`）的成熟用例。它定义了两条会延续到通用引擎的硬约束：
  - **盲测边界（market-blind）**：预测的*生成*环节任何时候不得读取市场价格/隐含概率来形成预测（走 `scripts/world-cup/` 的 `stripPrices`）。用户在通用引擎里贴的 context 若含市场价，生成路径必须拒绝，只能进"事后与市场对比"环节。此约束用 web 校验层（zod）+ 引擎层 guard 双闸强制（2026-06-11 用户决定，2026-06-19 细化）。
  - **事后评测**：`/world-cup/performance` 是给盲测预测打分的事后基准页，允许展示预测时刻的市场隐含概率算 Mock PNL / Brier / ECE——这不参与生成，不违反盲测。通用引擎沿用同一"生成盲测、评测可见市场"的分层。
- **明确不做（本期范围外，列出避免误解）**：
  - 不做任意自然语言事件到 Polymarket 市场的自动映射（事件↔市场匹配仍需结构化输入；这是引擎侧已知缺口，见 `docs/diagrams/prediction-engine-stage-flow.md`）。
  - 不做多元/连续结果预测，只做二元（Yes/No）。
  - 不做交易执行、不做钱包托管——产品只产出概率与依据。
  - MVP 不做"真节点级局部重算"（先做能精确做的"忽略证据即时重算"，加新料重算作为后续，理由见后续交互与成本节）。

### 1.6 锁定决策（截至 2026-06-21，部分待用户拍板）

> 沿用本仓 plan 文档惯例：✅ 已确认 / → 进行中 / 📋 待拍板。完整待拍板清单见后续"待用户拍板项"节。

- ✅ **产品形态**：左流右文档的活报告控制台（融合实时控制台 + 活文档 + 对话优先三种形态，非三选一）。
- ✅ **不重写引擎、不上 WebSocket**：在现有 SSE + 纯 reducer 上做增量扩展，反向通道用旁路 POST + 阶段边界采纳。
- ✅ **盲测双闸**：含市场价的 context 在生成路径拒绝，只进事后对比（web zod + 引擎 guard）。
- → **通用化**：以通用二元事件引擎为目标，世界杯为首个成熟用例（已是现状，无需新决策）。

## 2. 问题、目标与非目标

> 本节回答四件事：现在卡在哪、做完长什么样、用什么数字判定成功、明确不碰什么。结论先行——细节在 §5（统一交互形态）、§6（长任务架构）、§9（分阶段落地）展开。

### 2.1 一句话结论

把 `/research` 控制台从「跑完才弹结果的单向直播」升级成「边跑边能对话的活报告」：左边看着它推理、随时插话，右边一份会自我更新的结论文档；引擎不重写，断网能重连，用户说的话在下一个安全检查点被采纳并明确回流。

**三句话给 PM：**

1. 「动态过程展示」现有代码已做完 80–90%（7 阶段 SSE 流 + 纯 reducer + 5 张结果卡都能复用），缺的是把「跑完即弃」改成「常驻活报告」+ 补心跳防假死。
2. 「加 context」是改动最大的一项，统一走「旁路 POST + 阶段边界采纳」，不上 WebSocket。
3. 「交互」分两层：纯前端的即时操作（忽略某条证据→秒级重算）先上，需要引擎配合的「局部重算」作为第二步。

### 2.2 要解决的核心问题

当前 `apps/web/app/research/page.tsx` 的控制台能跑、能演示，但有三个把它挡在「可对话产品」门外的真实缺口。三个缺口都指向同一个根因——**整条流挂在一个 POST 的生命周期上，是单向的、无状态的、跑完即弃的**。

| # | 核心问题 | 用户侧表现 | 根因（真实文件） |
| --- | --- | --- | --- |
| P1 | **长任务像死机** | 一轮真 run 实测 12–15 分钟，其中渲染占 95%、静默 5 分钟以上属正常（见 `docs/diagrams/forecasting-cost-profile.md`），用户不知道它还活着 | `app/api/research/stream/route.ts` 无事件级心跳；只靠 SSE keep-alive，长静默在部分 CDN 会被掐断 |
| P2 | **不能加 context** | 用户中途想补一条背景、贴个链接当证据、说「这条别信」，没有任何上行通道 | 流是单向的——`lib/research/use-research-stream.ts` 只 POST 一次后单向读 `ReadableStream`，无反向写入接口 |
| P3 | **结果只读** | 结论卡、条件树、瀑布图、证据台账全部静态；`PredictionEvidence.url` 字段存在却没渲染成可点链接；不能忽略/降权某条证据看概率怎么变 | `components/research/result-charts.tsx` 的 5 张卡仅在 `phase==='complete'` 一次性渲染，无交互层 |
| P4 | **一断全丢、无历史** | 切后台、网络抖一下、刷新页面，整段推理就没了，无法恢复、无法回看、无法分享 | 同步流绑在请求生命周期上；`packages/db/src/schema.ts` 只有 `prediction_usage_events`（计费用），**没有任何 `research_runs` / `prediction_runs` 表** |

> **诚实补一刀（来自可行性审视）：** P1 的「12–15 分钟」画像来自 CLI / VPS orchestrator 实跑，而 C-end `/research` 的三条 driver 里，mock 12 秒就跑完、`vps-agent-driver.ts` 默认 `120_000ms`（2 分钟）就超时——**C-end 目前从未真正跑过一次 12–15 分钟的真 run**。所以「先回答 C-end 到底要不要接真长 run」是先决问题（见 §11 待拍板），心跳的价值兑现依赖长 run 真的接进来。

### 2.3 可量化目标

目标分「体验指标」与「工程门槛」两类。门槛是每个面向 `apps/web` 的改动都必须过的硬闸，不是加分项。

#### 体验指标（产品验收）

| 目标 | 当前 | 目标值 | 怎么测 |
| --- | --- | --- | --- |
| **不像死机** | 静默 5 分钟无任何信号 | 运行中**每 10–15 秒**至少一帧可见进度（心跳：当前阶段 + 已耗时 + 预计区间） | 抓 SSE 流，统计最大相邻帧间隔 ≤ 15s |
| **断网可恢复** | 断开即全丢 | 断线重连后从断点续传（靠 `Last-Event-ID` 只补发更大 seq，不重放整段），刷新页面能拉回完整快照 | 中途 kill 连接 → 重连 → 比对状态与未断时一致 |
| **加 context 有回流** | 无上行通道 | 插话后**立即**乐观回显「你说了…」，被采纳后变成「已在[称重]阶段采纳」并跟一条 `update.add` 显示概率怎么变 | 运行中 POST context → 断言收到 `context.applied` + 后续概率变更事件 |
| **证据可即时重算** | 台账只读 | 忽略/降权某条证据 → **前端秒级重算**贝叶斯瀑布与最终区间，**0 token** | 点「忽略此条」→ 断言概率在 1s 内更新、无网络调用 |
| **结论纯文本可读** | 关键数字埋在 SVG 里 | Yes 概率 + 80% 可信区间 + verdict 有纯文本/aria 等价表达（用户视力受限） | 屏幕阅读器走查 + 关闭 SVG 后结论仍可读 |

#### 工程门槛（每个 `apps/web` 改动必过）

- **本地 build 通过**：`pnpm --filter @autopoly/web build`（用 `build`，不要用 `exec next build`——后者跳过 prebuild，全新 worktree 会因 `@autopoly/*` 未构建直接失败）。
- **i18n 三语补齐**：所有面向用户文案进 `apps/web/lib/research/i18n.ts`（`en` / `zh` 至少齐；世界杯侧 `zh-TW` 为生成文件），不硬编码。
- **桌面 + 移动双视口自评**：截图 → 读图 → 自评；出现 console error / pageerror 视为未完成。
- **可追溯归档**：`contextLog` / `costActual` 写库；一轮 run 的实测开销追加进 `runtime-artifacts/pulse-live-cost-ledger/`。
- **诚实底线**：渲染持续 >15 分钟仍按 **regression** 处理，不放宽容忍度，不靠心跳给慢引擎打掩护。

### 2.4 明确非目标（不做什么）

把边界钉死，避免范围膨胀和返工。

#### 不做的技术选型

| 不做 | 为什么 | 替代方案 |
| --- | --- | --- |
| **不重写引擎** | 现有 7 阶段 SSE 协议 + 纯 reducer + 5 张结果卡是稳定地基，reducer `default` 分支已天然向后兼容未知事件（`lib/research/state-machine.ts`） | 在现有协议上**增量加事件类型**（`run.queued` / `heartbeat` / `context.applied` / `followup.*`），老 driver 零改动仍能跑 |
| **不上 WebSocket** | 与现有 SSE 全套不兼容，会逼着重写传输层 | 反向通道走**旁路 POST**（`POST /runs/{id}/context`），与现有单向 SSE 并存 |
| **MVP 不做真·节点级重算** | 引擎侧 stage 4–6 目前是自由 Markdown、不是类型化对象（见 `docs/diagrams/prediction-engine-stage-flow.md`），做不到精确的「只重跑 B 节点及下游」 | MVP 只做**能精确做的**：忽略某条证据→前端 0-token 重算；「加新料重算」短期诚实给等待反馈，待阶段类型化后再做真节点级 |
| **不把长任务塞进 Serverless 进程内** | 生产经 Vercel 自动部署，`route.ts` 是 `runtime = "nodejs"` 的 Serverless 函数：有墙钟硬上限、跨调用不共享内存，POST 创建的 run 与 GET 订阅的流会落在不同实例，进程内 store 必投递到错误实例 | 承载位置走**常驻进程**（raven-cloud / VPS orchestrator）+ run 状态落 **Postgres/Redis**；apps/web 只做代理 + 读快照（详见 §11 待拍板） |

#### 不碰的产品/政策边界

- **不破盲测**：预测的*生成*环节任何时候不读市场价/隐含概率来形成预测。用户贴的 context 若含市场价，**生成路径必须拒绝**（web 层 zod + 引擎层 guard 双闸），只允许进 `/world-cup/performance` 那类事后对比。这是 2026-06-11 / 06-19 用户锁定的硬约束。
- **不冒充一手核查**：用户提供的 context 一律标 `sourceType='用户提供'`、`reliability` 偏低且显式展示，绝不混进系统自己抓的一手证据。
- **不碰交易 / 执行器 / 风控参数 / 密钥**：本 PRD 范围是公开预测控制台（`apps/web` 非交易路径），任何触及交易、执行器、资金、不可逆操作的改动一律停下等用户确认。
- **不做这些功能**：自定义推理深度（仍只有 Norns 三档 urd/verdandi/skuld）、用户手动选 driver（仍由 env 决定）、KYC/AML、移动端原生 App。

#### 暂不承诺、留待拍板的（不是非目标，是「需用户决定才能定范围」）

- **C-end 是否真接真引擎**：还是 mock/demo 体验先行——这决定一半工程量是否现在投。
- **配额计费单位**：现按「每 run」计（`prediction-access.ts`：日 5 / 月 50 / 并发 1）。对话式产品追问频繁，两次对话就耗尽，须重定义计费单位——属产品策略，agent 不擅自定。
- **跨仓契约统一**：predict-raven（`stance: support/oppose`）与 raven-cloud（`stance: supports/weakens`）schema 已漂移，统一到一套是独立的跨仓工作项，须定迁移顺序。

## 3. 用户与核心场景

> 本章回答四件事：**这个产品给谁用 → 他们会怎么问 → 一次预测从头到尾长什么样 → 哪些需求倒逼了后面章节的架构决策**。所有自然语言样例、字段名、文件路径都对齐当前 `apps/web/app/research/` 控制台的真实实现，不是设想。

### 3.0 一句话结论（给 PM）

- 我们服务的不是"想要一个数字"的人，而是**"想看清这个数字怎么来的、并且想边看边插话"的人**——所以核心场景的重心从"输出一份报告"挪到"陪用户走完 12–15 分钟、并在中途接受他的输入"。
- 三个 persona 由轻到重：**好奇的浏览者**（只想看个热闹、点个样例）→ **做决策的专业用户**（要可信区间、要边际、要能否决某条证据）→ **内部运营/复盘者**（要历史、要成本、要盲测合规）。MVP 的钱主要花在第二类人身上。
- 自然语言查询天然分两类，都必须支持：**概率问**（"X 会发生吗？"，要的是 Yes 概率 + 80% 可信区间）和**决策建议问**（"我该不该买 / 现在这个价位值不值"，要的是边际 edge + 行动判断）。后者在**生成阶段受盲测约束**——引擎算概率时不许读市场价，市场对比只在结论环节做。

### 3.1 用户画像（Persona）

下面三个 persona 来自当前控制台已经支持的真实交互层（语言切换、tier 选择、可选市场价、样例 pill、配额系统），不是凭空捏造的人群。

#### Persona A · 好奇的浏览者（"先看个热闹"）

| 维度 | 描述 |
| --- | --- |
| **是谁** | 第一次进 `/research` 的访客；从 FinTwit / 朋友转发 / `forecasting-agent.com` 进来；可能没登录（`PredictionAccessMode = disabled` 演示态或 `unauthenticated`）。 |
| **核心诉求** | "这玩意儿到底靠不靠谱？给我看一个我看得懂的例子。" |
| **典型动作** | 不输入任何文字，直接点页面下方的样例 pill —— 当前是 `iran-nuclear`（Skuld 真实研究快照 2026-06-13，带真 URL）和 `fed-rate-cut`（演示）。点了即自动填充 composer 并跑起来（见 `sample-cases.ts`）。 |
| **最看重** | 跑起来别像死机、结论一句话能读懂、证据能点开看原文。 |
| **当前痛点** | 真 run 要 12–15 分钟，但**样例走 mock 只跑 12–14 秒**；真接长 run 时，现有 SSE 流"静默 5 分钟"会让这类用户以为页面挂了直接关掉。这正是**心跳指示器**要解决的体感问题。 |

#### Persona B · 做决策的专业用户（"我要拿这个数字做判断"）⭐ MVP 主力

| 维度 | 描述 |
| --- | --- |
| **是谁** | 已激活账号（`status = active`，走邀请码或自动激活域名）；FinTwit 重度用户、预测市场玩家、宏观/地缘研究者；视力可能受限（用户本人偏好可访问的纯文本结论 + 键盘可达，见 MEMORY）。 |
| **核心诉求** | "别只给我一个数。告诉我**区间多宽**、**和市场差多少（edge）**、**这条新闻你给了多少权重**——而且如果我觉得某条证据是噪音，我要能当场把它划掉看数字怎么变。" |

| **最看重** | `conclusion.confidenceInterval`（80% 可信区间，要标注是主观贝叶斯区间不是频率派）、`conclusion.edge`（模型 − 市场）、证据台账每条的 `stance / weightPct / reliability / node` 四元组、能否**否决某条证据即时重算**。 |
| **当前痛点** | 结果卡**完全只读**——证据台账不能筛、不能划掉、`url` 字段存在但没渲染成可点链接；运行中**完全不能插话**（composer 跑起来就 disabled）。这是本 PRD 最大的产品缺口。 |
| **成功标准** | 拿到一个他敢引用的概率 + 区间；至少做过一次"否决证据→看数字跳动"或一次追问；觉得这份报告比单纯一个百分比可信。 |

| 维度 | 描述 |
| --- | --- |
| **是谁** | 管理员（`role = admin`，由 `PREDICTION_ADMIN_EMAILS` 决定）；负责发邀请码、看配额、复盘预测质量、守盲测合规。 |
| **核心诉求** | "谁跑了什么、花了多少 token、有没有人想把市场价偷偷喂进生成环节、历史 run 还能不能调出来复盘。" |
| **典型动作** | 用 `scripts/prediction-invite.ts` 发码；查 `prediction_usage_events` 看用量；事后用世界杯 `/performance` 那套思路给预测打分（Brier / 校准 ECE，允许在事后环节展示市场隐含概率）。 |
| **最看重** | 可追溯归档（蓝图新增的 `contextLog` / `costActual` 字段）、盲测双闸是否真的挡住了市场价进生成路径、配额是否会因异步化而泄漏。 |
| **当前痛点** | **没有任何 `prediction_runs` / `research_runs` 持久化表**（`packages/db/src/schema.ts` 只有计费用的 `prediction_usage_events`）——run 跑完即弃，无历史、无快照、无法分享。配额并发计数靠 `status='running'` 行，异步化后若不由后台 worker 收尾会**泄漏**导致用户永远 429。 |
| **成功标准** | 能列出历史 run、能调出任意一次的完整推理链、确认没有市场价漏进生成环节。 |

### 3.2 典型自然语言查询样例

查询分两类。**关键约束：概率问和决策建议问在生成阶段都走盲测**——引擎形成概率时绝不读市场价（`stripPrices`），市场价只进结论的事后对比。下面每条都标了用户真正想要的输出字段。

#### 类型一 · 概率问（"会不会发生？"）

要的是 `conclusion.yesProbability` + `conclusion.confidenceInterval`。

| 用户怎么问 | 引擎给什么（真实字段） | 备注 |
| --- | --- | --- |
| "美国和伊朗能在 2026-06-30 前达成核协议吗？" | Yes 概率大字 + 80% 可信区间条 + 条件树 P(A)×P(B\|A)×P(C\|A,B) | 即当前 `iran-nuclear` 样例（Skuld 真快照），带 `asOf` / `deadline` |
| "美联储会在 2026 年 9 月前降息至少 50 个基点吗？" | 同上 | 当前 `fed-rate-cut` 演示样例 |
| "巴西能进 2026 世界杯四强吗？" | 同上 + `limitations` 局限说明 | 世界杯类问题强制盲测，生成环节不读盘口 |
| "这家公司会在 Q3 财报前发盈利预警吗？" | Yes 概率 + 区间 + 证据台账（每条挂到 A/B/C 节点） | 用户可在台账里**划掉**他认为已 priced-in 的那条 |

#### 类型二 · 决策建议问（"我该怎么做？"）

要的是 `conclusion.edge`（模型 − 市场）+ `verdict` + 行动含义。**必须提供市场价**才能算 edge，且市场价只在结论环节参与对比、不进生成。

| 用户怎么问 | 引擎给什么（真实字段） | 备注 |
| --- | --- | --- |
| "这个市场现在报 0.67，值不值得买 Yes？" | `edge = yesProbability − marketProbability` + verdict + 可信区间是否覆盖市场价 | 市场价填进 `marketPrice`，**生成阶段被 strip 掉**，只在 market 阶段对比 |
| "我手里这个仓还该不该拿着？" | 净 edge 判断（产品规则：净 edge 为负即建议减/平） | 对齐项目"持仓退出标准"——这是 C 端只读建议，**不下单** |
| "现在这个价位，模型觉得市场高估还是低估了？" | `edge` 的正负 + `verdict` 文字 + 边际来源（哪条证据撑起这个分歧） | 用户常接着追问"为什么"，触发 followup |
| "如果把截止日推到年底，结论会怎么变？" | 改判定参数的 what-if，重算受影响节点 | 这是"重档" context（改了事件定义本身），需 pause→recompute |

> **诚实边界（写进 PRD 防止过度承诺）**：决策建议问里的"值不值得买"是**只读分析**，不触发任何下单——C 端 `/research` 与交易执行层完全隔离。任何对话里的快速估计都必须标"非交易依据"。

## 4. 产品原则

> 这一节定义"产品该怎么取舍"的硬约束。下面每条原则都是**可执行的判断标准**，不是口号——评审一个交互、一段文案、一个接口能不能上线时，直接拿它对照。冲突时优先级：盲测边界 > 可信/可追溯 > 决策优先 > 去黑话 > 交互丰富度。

四条原则一句话先说清：

| 原则 | 一句话 | 违反时的表现 | 兜底机制 |
| --- | --- | --- | --- |
| 决策优先 | 用户第一眼看到的是"结论 + 概率 + 该信几分"，不是流程 | 把七阶段进度条当主角、结论藏在折叠区 | 结论卡永远在右栏顶部，运行中就开始跳动 |
| 去黑话 | 用产品经理能听懂的话，不用"贝叶斯/credible interval/edge"原文术语 | 文案直接写 "P(B\|A)=0.15"、"net edge -2pp" 当结论 | 术语首次出现配人话解释；i18n 文案过 voice 审查 |
| 可信 / 可追溯 | 每个数字都能点回到它的来源；演示数据明确标注"非真实推理" | demo 数字看起来像真核查；用户加的料冒充一手来源 | 证据四元组绑定到节点 + `sourceType='用户提供'` 标记 + costActual 归档 |
| 市场盲测边界 | 预测的**生成**环节永不读市场价；只在事后对比里可见 | 用户贴市场价被当背景喂进推理；隐含概率影响了结论 | web 层 zod 校验 + 引擎层 guard 双闸拒绝 |

---

### 4.1 决策优先（Decision-first）

**结论：用户打开报告，3 秒内必须拿到"会不会发生 + 概率多少 + 这个数字有多稳"，过程是可选的二级信息。**

这是从世界杯 `/research` 控制台已验证的产品方向延续过来的（见 MEMORY `forecasting-console-style`，2026-06-15 用户指令）。当前实现已经做对一半——结论卡（`result-charts.tsx` 的 `ConclusionCard`）确实是 5 张卡里视觉最重的一张，包含 Yes 概率大字 + 80% 可信区间条 + verdict 文案 + edge。但当前实现做错的另一半是**时序**：结论卡只在 `phase==='complete'` 时才渲染，用户要干等 12–15 分钟才看到任何结论。

落地到本控制台的三条硬规则：

1. **右栏结论卡从第 10 秒就在场**，初始灰显"仍在收敛"，随 `run.conclusion` / `update.add` 事件实时跳动。不要让用户为了看一眼当前判断而等到 `run.complete`。
2. **左栏的七阶段活动流是过程、不是主角**。已完成阶段收起成一行结论（`stage.exit` 的 `outcome`），只有当前 `activeStageId` 那一阶段展开吐 `progressLines`。这复用现有 `stage-timeline.tsx` 的折叠逻辑——它本来就是这么设计的，别退化成"七条进度条平铺一面墙"。
3. **追问（followup）也要决策优先**：用户问"换个截止日会怎样"，回的第一句必须是新概率和它相对原结论涨跌多少（复用 `UpdateWaterfall` 的 from→to 表达），而不是先复述一遍推理链。

判断标准：任何一屏，如果用户得先读完流程才能拿到结论，这屏就不合格。

---

### 4.2 去黑话（Jargon-free）

**结论：面向用户的每一句话都用"正常产品经理能理解"的表达；专业术语只在配套解释后出现，绝不拿术语原文当结论。**

这条同时受 MEMORY `forecasting-console-style`（去黑话、Manus 风格）和 `user-prose-style`（高信息密度、先给数字、砍掉对冲词）双重约束。具体到这个产品有三层：

**第一层 · 结论文案**：错误示范是把 `conclusion.yesProbability=0.62`、`edge=-0.02`、`confidenceInterval=[0.48,0.71]` 直接渲染成 "62% · edge -2pp · CI [0.48,0.71]"。正确做法是 `i18n.ts` 的 `c(locale, key)` 字典里给出人话版本——"约 62% 会发生，比市场略低（市场押 64%），但区间还比较宽（48%–71%），说明证据没把话说死"。`format.ts` 的 `pct()` / `pp()` 负责数字格式，文案负责把数字翻译成判断。

**第二层 · 术语首现即解释**：条件概率树、贝叶斯瀑布、可信区间这些必须出现的概念，首次出现时顺手解释"它是什么、影响什么"（见本 PRD 术语表）。可信区间尤其要标注"这是主观 80% 区间（贝叶斯），不是频率派置信区间"——当前实现这个 caveat 存在但不够显眼，本版要求它紧贴区间条。

**第三层 · 不用空词替代答案**：禁止用"框架/闭环/抓手/赋能/链路"这类词糊弄。讲方案先回答四件事——现在的问题是什么 / 影响什么 / 怎么处理 / 需要用户决定什么。涉及 driver、tier、token 预算这些基础设施细节时，先给人话结论再补技术细节。

**验收闸门**：所有面向用户的文案走 i18n（`apps/web/lib/world-cup/messages/` 的 `en`/`zh-CN`/`zh-TW` 三语补齐，`zh-TW` 为生成文件），不硬编码；新文案过一遍 voice 审查（house-style + 范例 + 编辑判分），确保高信息增益、不堆术语。这是 `apps/web` 用户可见改动"三件套"里 i18n 那一件的一部分。

---

### 4.3 可信 / 可追溯（Auditable & Traceable）

**结论：报告里每一个数字都能点回到产生它的来源；用户自己加的料明确标成"用户提供"且信度偏低；演示数据绝不冒充真实推理。**

可信度的最小单元是 `PredictionEvidence` 的四元组（`apps/web/lib/prediction-engine-demo.ts:24` 起）：

```
{ stance: 'support'|'oppose'|'mixed'|'neutral',  // 立场
  weightPct: number,                              // 对节点的影响 ±pp
  reliability: 0–1,                               // 信度
  node: 'A'|'B'|'C' }                             // 挂在哪个条件节点
```

这四个字段把"某条新闻"明确绑定到"拉高/拉低哪个条件节点多少 pp"——这是整份报告可审计性的地基。本版要做三件事把它从只读升级为可追溯：

1. **证据台账可下钻**：`EvidenceLedger` 每行可点开看 `excerpt` + `url`（当前 `url` 字段存在但没渲染成可点链接，是已知缺口），且新增 `provenance` 字段记录"哪条证据喂给了哪个 stage/node"，让用户从结论一路点回原文。
2. **用户提供的料如实标注**：用户通过反向通道加的 `ContextItem` 一律打 `sourceType='用户提供'`、`reliability` 偏低、在台账里高亮显示——绝不冒充成引擎自己做的一手核查。这既是诚信要求，也是防注入（恶意 prompt 当 context 喂进模型）的前提。
3. **演示数据明确标记**：mock driver 产出的 run 标 `mode='demo_read_only'`，所有数字由 `eventText` 哈希确定性生成。这类数据**看起来可以很真**，所以 UI 必须显式标注"演示/非真实推理"。

**诚实管理预期（这条最容易被违反）**：当前 api-driver 的 live 路径只是把模型文本当旁白叠在 demo 骨架上，**数字仍是 demo 生成的**（`api-driver.ts:101` 的 `TODO(integration)` 写得很清楚：把 `emit` 从"事后旁白"换成"模型按 JSON schema 吐 evidence/model/conclusion + zod 校验"才算数字变真）。在这一笔打通前，凡是基于"忽略某条证据→即时重算"的交互，重算的都是 **demo 数字**，不是真模型数字——MVP 卖点必须诚实标注这层，不能让用户以为自己在调整真实推理。

**可追溯归档**：每次 run 写 `costActual`（elapsedMs / inputTokens / outputTokens / externalCalls / llmCalls）+ `contextLog`（用户加过哪些 context、对哪个节点产生何影响）。这对齐项目"所有关键运行产出可追溯归档"的约定，开销数字按约定追加进 `runtime-artifacts/pulse-live-cost-ledger/`。

### 4.4 市场盲测在通用场景的边界（Market-blind Boundary）

**结论：预测的"生成"环节任何时候不得读取市场价格/隐含概率；市场数据只允许出现在"事后与市场对比"环节。这是项目硬约束（2026-06-11 用户决定，2026-06-19 细化），不是可调参数。**

这条在世界杯产品里已经落地（`scripts/world-cup/` 的 `stripPrices`，见 `check-updates.ts:23` / `cache-markets.ts:20`——抓市场数据时直接剥掉价格字段，只保留事件结构与结算映射）。通用预测引擎要把同一条约束扩展到**任意用户问题 + 反向通道加 context**这两个新场景，难点在于：用户可能主动贴市场价当"背景"，必须挡住。

**双闸设计**：

| 闸 | 位置 | 拦什么 |
| --- | --- | --- |
| 闸一 · web 校验层 | `POST /runs` 与 `POST /runs/{id}/context` 的 zod schema | `ContextItem` 里含市场价/隐含概率的，在生成路径直接拒绝（返回明确错误，不静默丢弃） |
| 闸二 · 引擎层 guard | driver 读取 context 队列时 | 兜底再查一次，防 web 层被绕过；含价信息只准进"市场对比"阶段 |

**边界划清楚——什么允许、什么禁止**：

- ❌ **禁止**：预测生成的任何 stage（definition → query-design → evidence → weighting → model → bayes）读市场价；用户贴的市场价进入这些 stage 当输入。
- ✅ **允许**：第 7 个 stage（market）做事后对比——展示 Polymarket 在预测时刻的隐含概率、算 edge（模型 − 市场）、Mock PNL / Brier 技巧分 / 校准 ECE。这是给盲测预测"打分"，不参与生成，所以不违反盲测（对齐 2026-06-19 细化：`/world-cup/performance` 事后基准评测页的同一逻辑）。
- ✅ **允许**：用 `marketProbability` 字段渲染区间条上的市场红线 marker——因为它只在结论展示层、不回流进推理。

**为什么这条优先级最高**：它是真钱实盘项目的政策底线，任何"市场盲测等政策"相关改动按项目规则必须停下等用户确认，agent 不得擅自放宽。所以盲测 guard 的放置层（web-only 还是双闸）本身列为待用户拍板项——但默认必须是双闸，宁可严不可松。

---

### 4.5 交互（Interactive，从只读直播升级为可对话报告）

**结论：报告不再是"跑完才弹出的只读文档"，而是"边长边能对话"的活报告——但交互按风险分两层、由轻到重上线，每一档都诚实标注"何时真正生效"。**

当前实现的交互完全在输入侧（textarea、tier 选择、market 输入、run/reset 按钮、sample 案例 pill），**结果区是纯只读**——证据台账不能筛选排序、结论条只是视觉、树和瀑布流完一次就静止（这是 `gapsAndLimits` 点名的最大可交互性缺口）。本版分两层补：

**第一层 · 纯前端即时交互（先上，性价比最高，零引擎改动）**

- 证据台账每行可"忽略 / 降权 / 提权"，点了**本地即时重算**最终概率和区间（秒级、0 token，因为只是权重调整）。
- 节点 / 来源 / 局限全部可展开折叠——给 `ResearchStageState` 和 model 节点加一个 `expanded` 位，把现在"单活跃阶段展开"泛化为"任意节点可独立展开"。默认只展开当前活跃节点、看完折叠成一行，防信息过载。
- `url` 字段渲染成可点链接。

> ⚠️ 即时重算的诚实边界：见 4.3——在 api-driver 数字变真之前，这一层重算的是 demo 数字。能精确做、秒级做的是"忽略证据"这种纯权重调整；"加一条新料后重算"短期只能近似（重跑受影响阶段）并明确给等待反馈，不假装即时。

**第二层 · 需引擎配合的局部重算（第二步）**

- 运行中"插话"加 context：走旁路 `POST /runs/{id}/context`，在**阶段边界采纳**（`stage.exit` 后、下一个 `stage.enter` 前读队列），采纳后发 `context.applied` 事件回流 + 后续 `update.add` 显示概率怎么变。
- 体感承诺要诚实：用户输入**即时被确认**（乐观回显一条"你说了…"气泡），**实际生效在下一个安全检查点**（变成"已在[称重]阶段采纳"）。绝不假装即时改写已经算完的阶段。
- 运行后追问走 `followup`：生成一个继承父 run 证据池的子 run，只重算相关节点，不重跑整管线、省 token。

**底层支撑（详见后续架构章节）**：插话能成立的前提是把"同步流式"改成"异步 run + 可重连流"——`POST /runs` 秒回 runId、`GET /runs/{id}/stream` 独立订阅可断线重连。否则现有单向 SSE（`use-research-stream.ts` 用 fetch 流手动分帧，不是原生 `EventSource`）既不能重连也没有上行通道。这是交互原则能否兑现的工程地基，不是本节展开的范围。

**可访问性要求（硬约束，因用户视力受限）**：节点展开、SVG 图表（区间条 / 条件树 / 瀑布）、插话输入框都要补 `aria` 标签 + 键盘可达；关键结论保证**纯文本可读**，不能只靠图形传达。这条对所有交互一视同仁，包括 sub-agent 做的前端改动。

### 4.6 原则之间怎么取舍（速查）

当两条原则在某个具体设计上打架，按下表裁决：

| 冲突场景 | 怎么判 | 依据原则 |
| --- | --- | --- |
| 用户贴了市场价想当证据 → 想做得"好用"直接采纳 vs 盲测拒绝 | **拒绝进生成**，只进事后对比，并给明确提示 | 盲测 > 交互 |
| 即时重算很酷 → 但当前算的是 demo 数字 | 照做但**明确标注非真实推理** | 可信 > 交互 |
| 结论文案想精确 → 写成 "P(B\|A)=0.15" | 改成人话，精确数字进可展开的节点 rationale | 去黑话 > （表面的）精确 |
| 想把七阶段全程展开"显得透明" | 折叠成一行结论，过程是二级信息 | 决策优先 > 过程展示 |

一句话收尾：**这个产品的差异化不在"能展示多复杂的推理"，而在"让用户三秒看懂结论、随时能质疑它、并且每个数字都查得到根"——复杂度服务于这三件事，不反过来。**

## 5. 核心交互体验（重点）

> 本章是整份 PRD 的产品核心。它回答一件事：**一次要跑 12–15 分钟的预测，用户在这 15 分钟里到底看到什么、能做什么、说的话会怎么被采纳。** 三大难题（过程可见、自主加 context、可对话精修）的最终方案集中在这里。技术承载（异步 run、可重连流、API 表面）放在第 6/7 章，本章只在必要处点到为止。

### 5.0 结论先行（给 PM 三句话）

1. **统一形态 = 左流右文档**：屏幕左边是一条实时活动流（看着它推理、随时插话），右边是一份会自我更新的活报告（结论卡 / 条件树 / 贝叶斯瀑布 / 证据台账）。这不是三选一，是把三个内部提案融合成一个界面。
2. **三大难题各有诚实答案，不画饼**：① 过程可见 = 复用现有 7 阶段流 + 加心跳（现有代码已完成 80–90%）；② 加 context = 旁路 POST + 阶段边界采纳（绝不上 WebSocket）；③ 交互 = 纯前端即时层（忽略某条证据→秒级重算）先上，引擎配合的局部重算第二步。
3. **一个真实前提先说清**：当前 C-end `/research` 控制台从没真正跑过一次 12–15 分钟的真 run——mock driver 约 12 秒就走完，VPS driver 当前 `120s`（`vps-agent-driver.ts:53`）就超时。心跳要解决的"假死体感"，**只有等真引擎 + 长任务承载（第 6 章）接进来才会真正出现**。所以本章描述的是目标形态，心跳/可重连等增量的价值兑现依赖第 6 章的承载层先落地。

### 5.1 主屏布局：左流右文档

运行中是主战场。屏幕一分为二，两栏共享同一条事件流、同一份 reducer 状态（`ResearchState`，见 `apps/web/lib/research/state-machine.ts`）。

| 区域 | 内容 | 现状 | 改动量 |
| --- | --- | --- | --- |
| **左栏 · 状态条** | `running · 阶段 5/7 · 已耗时 8m12s · tier=skuld · driver=vps` | 已有 `StateMachineLegend`（phase pill + 阶段轨道） | 加"已耗时"实时计时 + 心跳驱动 |
| **左栏 · 实时活动流** | 已完成阶段收起成一行结论；当前阶段展开吐"思考旁白"(`progressLines`) + 产出物（证据/模型/贝叶斯行） | 已有 `StageTimeline`，逻辑可复用 | 容器从纵向单列改成左栏 |
| **左栏 · "仍在工作"指示器** | 当前在干嘛 + 已耗时 + 该阶段预计区间，由心跳驱动会动 | **新建**（依赖心跳事件） | 小 |
| **左栏 · 常驻插话框** | 运行中也可用，加 context / 加 source / 纠偏；输入先乐观回显"你说了…" | **新建**（当前 composer 运行中被禁用） | 中 |
| **右栏 · 活报告** | 从第 10 秒就铺好 7 阶段 + A/B/C 节点 + 来源区空位（灰显），内容一格格"长"进去 | 5 张结果卡组件可复用（`result-charts.tsx`），但**当前只在 `phase==='complete'` 渲染** | 中（渲染时机从 complete-only 改成 streaming-growing） |

右栏活报告的五块内容（叶子组件全部可复用，外壳新写）：

- **结论卡**：Yes 概率大字 + 80% 可信区间条（标注"主观区间，非频率派"）+ 市场红线 marker；随贝叶斯更新实时跳动并标"仍在收敛"。组件 `ConclusionCard` + `ConfidenceBar`。
- **条件概率树**：`P(A) × P(B|A) × P(C|A,B)`，节点可点开看 `rationale`。组件 `ConditionalTree`。数据来自 `PredictionModelNode`（`id/label/probability/rationale`）。
- **贝叶斯瀑布**：台阶图，prior → 每吸收一条证据涨/跌一截 → posterior。组件 `UpdateWaterfall`。数据来自 `PredictionUpdate`（`label/from/to/explanation`）。
- **证据台账**：按 `|影响|` 排序的表格，每行 = 立场色块 / 标题+日期+来源 / 影响 ±pp / 信度 0–1 / 挂在哪个节点。组件 `EvidenceLedger`。**本方案把它从只读升级为可交互**（见 5.4）。
- **局限说明**：`limitations[]`，可展开。

> ⚠️ **诚实标注复用边界**：可复用的是**叶子展示组件 + 纯 reducer + format/i18n**；"左流右文档"双栏外壳、常驻文档、可交互层、移动端坍缩**全是新写**。说"复用 80–90%" 仅指叶子组件，不要让这句话掩盖外壳重构。

**可访问性（硬约束，用户视力受限）**：节点展开、SVG 图表（条形/瀑布/树）、插话框必须补 `aria` + 键盘可达；**关键结论必须有纯文本可读路径**（不能只靠 SVG 视觉传达概率与区间）。三件套验收同时纳入 i18n 三语（`en`/`zh-CN`/`zh-TW`）+ 桌面/移动双视口自评 + 本地 `pnpm --filter @autopoly/web build` 通过。

### 5.2 难题一 · 动态决策过程如何可见

**问题**：一次真 run 要 12–15 分钟，其中渲染占 95%，实测"静默 5 分钟属正常"（见 `docs/diagrams/forecasting-cost-profile.md`）。用户干等 14 分钟、屏幕不动，会以为死机。

**方案 = 复用现有 7 阶段 SSE 流 + 两件小事**，不重写引擎。

**(a) 心跳防假死**：在 `events.ts` 的 `ResearchEvent` 判别联合里新增两类事件，每 10–15 秒发一帧：

```ts
| { type: "run.heartbeat"; seq: number; ts: string; stageId?: string; elapsedMs?: number; etaRangeSec?: [number, number] }
| { type: "stage.heartbeat"; stageId: string; seq: number; elapsedMs: number; etaRangeSec?: [number, number] }
```

reducer 加对应 `case`（现有 `default` 分支已验证会安全吞下未知事件，见 `state-machine.ts:182`，所以老 driver 零影响），UI 显示一个会动的"仍在工作"指示器：把"静默 5 分钟"翻译成人话——`正在[称重]阶段 · 已 3m20s · 预计还需 1–3 分钟`。

**(b) 活报告骨架**：从第 10 秒就把右栏文档框架铺出来（7 阶段 + A/B/C 节点 + 来源区，灰显占位），内容顺着事件一格格长进去，用户全程有得看、有得点，而不是干等一次性弹出。`run.accepted` 事件已携带 `stages: ResearchStageMeta[]`，骨架数据现成。

**诚实底线**：心跳是改善体感，**不是给慢引擎打掩护**。渲染持续 >15 分钟仍按 regression 处理（不放宽容忍度），符合 cost-profile 约定。心跳工作量 1–2 天，但价值兑现依赖真长 run 接进来（见 5.0 第 3 条）。

| 子项 | 状态 |
| --- | --- |
| 7 阶段流 + reducer + 5 张卡 | 现成 |
| 心跳事件 + reducer case + UI 指示器 | 新建（1–2 天） |
| 活报告骨架（complete-only → streaming-growing） | 新建（中） |

### 5.3 难题二 · 用户如何自主加 context

**问题**：用户运行中突然想到一条背景、一个链接、或想否决某条证据——现有流是**单向**的（只能看不能说）。

**方案 = 旁路 POST + 阶段边界采纳**，绝不上 WebSocket（与现有 SSE 全套不兼容）。统一一个上行接口 `POST /api/research/runs/{id}/context`，按改动轻重分三档：

| 档位 | 入口/时机 | 作用与生效路径 | 成本 |
| --- | --- | --- | --- |
| **轻档**：贴一段话 / 一个链接当背景或证据候选 | 运行中任意时刻，左栏插话框 | 写进按 `runId` 的共享 store；driver 在每个**阶段边界**（`stage.exit` 后、下一个 `stage.enter` 前）读一次待处理队列，采纳后发 `context.applied` 事件回流 + 后续 `update.add` 显示概率怎么变 | 约 1 次便宜 LLM，秒级 |
| **中档**：忽略 / 锁定某条证据 | 证据台账行内按钮 | 纯权重调整，**前端即时重算**贝叶斯瀑布 | 秒级、0 token |
| **重档**：改判定参数（如换截止日） | 插话框 / 浮层 | 改变了"事件定义"本身，需经 `/control` 接口 `pause→recompute`，触发受影响节点局部重跑 | 部分重跑 |

**新增事件**（紧跟 `update.add`/`model.add` 显示概率怎么变）：

```ts
| { type: "context.applied"; contextId: string; summary: string; affectedStageId?: string; affectedNodeId?: string }
```

**ContextItem 数据结构**（新增，加 context 核心）：

```ts
{ id, kind: 'note' | 'url' | 'evidence_override' | 'param_override',
  value: string, stance?: 'support' | 'oppose' | 'neutral',
  targetNodeId?: 'A'|'B'|'C', targetEvidenceId?, weightHint?, createdAtUtc }
```

**体感承诺（诚实）**：输入**即时被确认**（乐观回显气泡"你说了…"），但**实际生效在"下一个安全检查点"**（阶段边界），收到后端确认后气泡变成"已在[称重]阶段采纳"。绝不假装即时改写已经算完的阶段。

> ⚠️ **真引擎上的现实边界**：阶段边界采纳在 mock/replay 链可做（replay 循环里加一个 `await drainContextQueue(stageId)` 检查点）。但真引擎（VPS orchestrator / `daily-pulse-core`）目前是 CLI 批处理、一次性产出 `pulse.json`，**不是能在阶段间停下来听外部输入的常驻进程**。所以 MVP 阶段：**运行中加 context 的真实生效仅在 mock 链可演示；真引擎链上短期只支持"运行后 followup 子 run"**（新建 run，不要求中断旧 run，相对现实）。

**盲测双闸（硬约束）**：用户贴的 context 若含市场价格 / 隐含概率，**生成路径必须拒绝**（zod schema + 服务端 guard 双闸），只允许进"事后与市场对比"环节（符合 2026-06-11/19 用户决定）。用户提供的 context 一律标 `sourceType='用户提供'`、`reliability` 偏低且显式展示，绝不冒充一手核查；URL 抓取设白名单+超时，note 走注入检测。

### 5.4 难题三 · interactive 体验（追问 / 精修 / 分支）

**问题**：现在报告跑完即只读——证据台账不能筛选/排序，结论条只是视觉，树/瀑布静态，`url` 字段存在但没渲染成可点链接。

**方案 = 分两层，按风险递增上线。**

**第一层（纯前端、先上、性价比最高）**——不需要引擎配合：

- 证据台账每行可 **忽略 / 降权 / 提权**，点了**本地即时重算**最终概率和区间（秒级、0 token，因为是纯权重计算）。
- 节点 / 来源卡 / 局限 **全部可展开折叠**：给 `ResearchStageState` 和 `PredictionModelNode` 加 `expanded` UI 状态位（前端态，可不入持久化）。默认只展开当前活跃节点、看完即折叠成一行摘要，防"信息过载变一面墙"。
- `url` 字段渲染成**可点链接**（当前未渲染，是个低成本即得项）。

**第二层（需引擎配合、第二步）**——对话/分支驱动：

- **局部重算**：只重跑受影响的节点及下游，而不是整轮 12–15 分钟。
- **追问（followup）**：对已完成报告提问（如"为什么 B 节点只给 0.15""换个截止日会怎样"）→ 生成一个**继承父 run 证据池的子 run**，只重算相关部分、省 token。接口 `POST /runs/{id}/followup`，返回 `followup.progress` / `followup.answer` 流。
- **分支 / 版本对比**：追问叠加新一轮事件到同一份报告，冻结成报告版本（v1 22% → v2 28%，复用 `UpdateWaterfall` 思路展示差异）。
- 可选的**暂停 / 继续 / 提前结论**（"够了就停"），走 `/control` 接口。

> ⚠️ **冲突仲裁（局部重算到底能不能真"局部"）**：三个内部提案判断不一，统一采纳最诚实口径——
> - MVP 主卖点 = "忽略某条证据→前端秒级重算"（能精确做、0 token）。
> - "加新料重算节点"短期用"重跑受影响阶段"近似，**并诚实标注等待**，不假装即时。
> - 真正的节点级重算，**待引擎侧把 stage 4–6 从自由 Markdown 升级为类型化对象后**（证据加权 / 结构模型 / 贝叶斯，当前在 Pulse 里仅 partial）再做——这是引擎侧最大真实工作量，不在"不重写引擎"承诺内的轻量项。

**配额冲突（需用户拍板）**：现配额按"每 run"计（日 5 / 月 50 / 并发 1，见 `prediction-access.ts`）。对话式产品追问频繁，两次对话就会把日配额耗尽，须重定义计费单位（按会话？整轮 vs 局部重跑分级？）——属产品策略，agent 不擅自定。

### 5.5 交互流程与状态机

整套交互建立在现有两层嵌套状态机之上（运行相位 + 阶段状态，见 `state-machine.ts`），本章新增的事件全部走同一条 reducer，老 driver 因 `default` 分支天然向后兼容。

**运行相位（Run Phase）：**

```
                 run.accepted              run.complete
   [idle] ───────────────────▶ [running] ───────────────▶ [complete]
                                   │  ▲
                  run.error        │  │ context.applied / heartbeat
   [idle] ───────────────────────▶│  │ (停留在 running，不改相位)
                                   ▼  │
                                [error]
```

**单次预测的完整交互时间线（目标形态）：**

```
T+0s    用户输入事件文本 → 选 tier → Run
        POST /api/research/runs → 秒回 runId (status=queued)        [run.queued]
T+0s    GET /runs/{id}/stream 独立订阅（断网可重连，靠 Last-Event-ID 续传）
T+10s   右栏铺好活报告骨架（7 阶段灰显占位）                          [run.accepted → stages]
循环：   每个阶段 ─ stage.enter → progressLines + 证据/模型/贝叶斯行 → stage.exit
        每 10–15s 发心跳 → 左栏"仍在工作"指示器会动                  [run.heartbeat]
─── 任意时刻：用户在左栏插话 ───────────────────────────────────────────────────
        前端立刻显示"你说了…"气泡（乐观回显）
        POST /runs/{id}/context (202 accepted)
        → 引擎在下一个阶段边界采纳 → 气泡变"已在[称重]阶段采纳"      [context.applied]
        → 后续概率变化实时回流                                       [update.add]
─── 运行中：用户点证据台账"忽略此条" ──────────────────────────────────────────
        前端本地即时重算贝叶斯瀑布 + 结论区间（0 token，秒级）
─────────────────────────────────────────────────────────────────────────────
T+~14m  run.conclusion → run.complete（报告冻结成版本）             [run.complete]
T+完成   用户追问 → POST /runs/{id}/followup → 子 run 继承证据池       [followup.*]
        → v1 22% → v2 28% 版本对比
```

**关键状态保证（向后兼容）：**

| 保证 | 机制 |
| --- | --- |
| 老 driver 不发新事件也不崩 | reducer `default` 分支吞未知事件（`state-machine.ts:182-183`，已验证） |
| 插话不改运行相位 | `context.applied` / `heartbeat` 在 `running` 内处理，不触发 phase 切换 |
| 断网重连不重放整段 | 每帧加 `id:<seq>`，重连按 `Last-Event-ID` 只补发更大 seq（注：现有 `encodeResearchEvent` 无 `id:` 行、客户端用 `fetch` 流而非原生 `EventSource`，续传需扩传输层，见第 6/7 章） |
| 只读升级为可对话 | `expanded` 状态位 + 前端权重重算 + followup 子 run，分两层上线 |

### 6.0 一句话与三句结论（给 PM）

- **整体形态 = 左流右文档**：左边是一条实时活动流，你看着引擎一步步推理、随时插话；右边是一份会自我更新的"活报告"（Living Forecast），从第 10 秒就铺好骨架、内容一格格长进去，跑完就冻结成一个可回看的版本。
- **三件事必须当面讲清楚，不画饼**：(1) 12–15 分钟不能像死机——靠**心跳**把"静默 5 分钟（实测正常）"翻译成会动的"仍在工作"；(2) 运行中能加料——靠左下角**常驻插话框**，输入即时回显、在下一个安全检查点真正生效；(3) 报告不是只读的——证据可"忽略此条"秒级重算、节点/来源/局限可展开、URL 可点。
- **诚实边界**：当前 C-end `/research` 控制台是**单列、跑完才出结果卡**的渐进式布局（`apps/web/components/research/research-console.tsx`），改成"左右双栏 + 结果卡随流增长"是**外壳重构**——5 张结果卡的绘制函数可复用，容器/布局/交互层是新写。本章描述的是目标态，不是现状。

### 6.3 运行控制台主屏（运行中 = 主战场）

`phase=running` 时的目标布局——**左栏活动流、右栏活报告**，两栏共享同一条 SSE 事件流（`events.ts` 的 `ResearchEvent` 判别联合）。

#### 6.3.1 左栏：实时活动流 + 心跳 + 插话

| 区块 | 关键元素 | 数据来源 |
| --- | --- | --- |
| **顶部状态条** | `running · 阶段 5/7 · 已耗时 8m12s · tier/driver` | `state-machine-legend.tsx` 现有 phase pill + 阶段轨道 |
| **活动流主体** | 已完成阶段收起成一行结论；当前阶段展开吐"思考旁白"(`stage.progress` 的 `progressLines`) + 产出物（证据/模型/贝叶斯行） | `stage-timeline.tsx`（现有，Manus 式可折叠卡） |
| **心跳指示器** | 会动的"仍在工作：[当前阶段] · 已耗时 8m12s · 预计 2–4 分钟" | **新增事件** `run.heartbeat` / `stage.heartbeat`（每 10–15s 一帧，带 `elapsedMs` + `etaRangeSec`） |
| **常驻插话框** | 运行中也可用，支持"加 context / 加 source / 纠偏" | **新增** `POST /runs/{id}/context`，旁路上行，绝不上 WebSocket |

**心跳是诚实的体感修复，不是给慢引擎打掩护**：成本画像实测一轮 run ≈ 12–15 分钟、渲染占 95%、静默 5 分钟正常（`docs/diagrams/forecasting-cost-profile.md`）；心跳把这段沉默翻译成人话。渲染持续 >15 分钟仍按 regression 处理，不放宽容忍度。

#### 6.3.2 右栏：活报告骨架（随流增长）

一开始就铺好 **7 阶段 + A/B/C 节点 + 来源区**的空位（灰显），内容顺着事件一格格长进去——而不是干等 14 分钟一次性弹出。具体卡片见 6.4。

#### 6.3.3 插话确认与采纳回流

每次插话先**乐观回显**一条"你说了…"气泡（不等后端确认），收到 `context.applied` 事件后变成"已在[称重]阶段采纳"。诚实承诺：输入即时被确认、**实际生效在下一个安全检查点（阶段边界）**，绝不假装即时改写已算完的阶段。

**移动端**：双栏在窄屏坍缩为**单列 + 顶部 Tab 切「活动流／报告」**；插话框吸底；心跳指示器作为状态条第二行常驻。坍缩设计是新的移动端工作量，纳入桌面+移动双视口自评。

### 6.4 分析报告面板（活报告的五张卡）

`phase=complete` 解锁完整报告（运行中右栏已逐格长出）。五张卡复用 `result-charts.tsx` 的绘制函数，但从"只读"升级为"可点可改"。**结论必须保证纯文本可读**（用户视力受限）。

#### 卡 1 · 结论卡（最大视觉）

- **Yes 概率大字** + **80% 可信区间条**（0–100% 轨道 + 蓝色带 + 白点 + 市场红线 marker）+ verdict 文案 + edge（模型 − 市场）。
- 绑定 `conclusion: { yesProbability, confidenceInterval:[lo,hi], marketProbability, edge, verdict }`（`prediction-engine-demo.ts:74-80`）。
- 区间须显式标注**80% 主观可信区间（贝叶斯，非频率派）**。运行中随 `update.add` 实时跳动并标"仍在收敛"。

#### 卡 2 · 条件概率树 P(A) × P(B|A) × P(C|A,B)

- 绑定 `model: PredictionModelNode[]`（`{ id, label, probability, rationale }`，`:35-40`）。
- **每个节点可点开看 `rationale`**（"为什么给这个数"）——补上"tree 不能下钻"的现状缺口。新增前端 `expanded` 位（不入持久化亦可）。

#### 卡 3 · 贝叶斯瀑布

- 台阶图：prior 起步、每吸收一条证据涨/跌一截、收敛到 posterior。绑定 `updates: PredictionUpdate[]`（`{ label, from, to, explanation }`，`:42-47`）。

#### 卡 4 · 证据台账（Evidence Ledger）

按 |影响| 排序的表格，绑定 `evidence: PredictionEvidence[]`（`:22-33`）。每行四元组是**整份报告可审计的最小可信单元**：

| 列 | 字段 | 升级点 |
| --- | --- | --- |
| 立场 | `stance: 'support'｜'oppose'｜'mixed'｜'neutral'`（绿/红/金/灰） | — |
| 标题+日期+来源 | `title` / `date` / `sourceType` | **点开看 `excerpt` + `url` 可点链接**（现状 `url` 存在但未渲染成链接） |
| 影响 ±pp | `weightPct` | — |
| 信度 0–1 | `reliability` | 用户提供的证据高亮标"用户提供"、`reliability` 偏低 |
| 节点 | `node: 'A'｜'B'｜'C'` | — |
| 操作 | — | **"忽略此条"→ 前端秒级 0-token 重算**贝叶斯瀑布与最终概率 |

> **诚实标注**：在 api-driver 的"数字变真"打通前（`api-driver.ts:103` `TODO(integration)`），"忽略某条证据→秒级重算"重算的是 demo 骨架数字，不是真模型数字。MVP 卖点须标这层。

#### 卡 5 · 局限说明

绑定 `limitations: string[]`，可展开看详情。

**移动端**：五卡纵向堆叠；条件树横向溢出时改纵向连乘；瀑布图 SVG 按窄屏 viewBox 重排；台账表格保留关键三列（立场/影响/节点），其余进行内展开。SVG 图表 + 节点展开 + 插话栏均补 `aria` 标签与键盘可达。

### 6.5 Context 抽屉（加料的可追溯入口）

**目的**：让用户一眼看清"我往这次预测里加过哪些料、每条把哪个节点的数改了多少"。

- **加 context 预检浮层**（贴链接/附件时弹出）：确认 stance（支持/反对/中性）+ 归到哪个节点（A/B/C）+ **醒目盲测提示**（含市场价会被拒绝）+ 是否触发重算。
- **Context 抽屉内容**：列出 `contextLog: ContextItem[]`，每条 `{ id, kind:'note'｜'url'｜'evidence_override'｜'param_override', value, stance?, targetNodeId?, createdAtUtc }`，并显示对应的 `context.applied` 摘要（"在[称重]阶段采纳，B 节点 0.15→0.18"）。
- **三档由轻到重**（详见三大难题章）：轻档=贴话/链接当背景；中档=忽略/锁定某条证据（纯前端 0 token）；重档=改判定参数（如换截止日，经 pause→recompute）。

**移动端**：抽屉从底部上滑（bottom sheet）；预检浮层占满宽度、盲测提示置顶不可错过。

## 7. 系统架构

> 本章回答四件事：(1) 前端、API、引擎、raven-cloud 是什么关系，谁负责什么；(2) 实时进度怎么从引擎流到用户屏幕（SSE）；(3) 一次 12–15 分钟的长任务在工程上怎么承载（异步化 + 可重连）；(4) 这套东西部署成什么形态、当前部署形态对架构有什么硬约束。
>
> **一句话结论**：现有架构是「单次 POST 同步流式」——浏览器发一个 POST，整条 12–15 分钟的流就挂在这个请求的生命周期上。这在本地 Node 能跑、在 mock（12 秒）能跑，但**在生产的 Vercel Serverless 上跑不完长任务**（单函数有墙钟硬上限）。所以本章的核心架构决策是：**把同步流式改成「异步 run + 可重连流」**，并明确「长任务承载进程放哪」是开工前必须拍板的前置阻塞项，不能再走「先在 apps/web 出可用版」这条路。

### 人类 review 入口（先看这 5 处再看下文）

| # | 文件 / 配置 | 为什么是关键 |
| --- | --- | --- |
| 1 | `apps/web/vercel.json` | 当前内容只有 `{"framework":"nextjs"}`，**没有 `maxDuration`**。这决定了长任务在生产环境的墙钟上限（Vercel 默认 60s）。 |
| 2 | `apps/web/app/api/research/stream/route.ts:20` | `export const runtime = "nodejs"` + `dynamic = "force-dynamic"`，整条流目前挂在单个 POST 上。异步化要从这里拆。 |
| 3 | `apps/web/lib/research/events.ts:77` | `encodeResearchEvent` 输出 `event: <type>\ndata: <json>\n\n`，**没有 `id:` 行**——续传机制的改造点。 |
| 4 | `apps/web/lib/research/use-research-stream.ts:66/97` | 客户端用 `fetch`+`ReadableStream` 手动分帧，只认 `startsWith("data:")`，**不是浏览器原生 `EventSource`**——所以 SSE 标准的「Last-Event-ID 自动续传」不会自动生效。 |

### 7.1 四个组件，各自负责什么

整条链路是「前端 ↔ API ↔ 引擎 ↔ raven-cloud」四层。先给职责，再给关系图。

| 组件 | 是什么 | 负责 | **不**负责 |
| --- | --- | --- | --- |
| **前端控制台** `apps/web/components/research/` + `app/research/page.tsx` | 用户唯一看到的界面（活报告控制台） | 渲染左流右文档、发起 run、订阅流、把事件喂给纯 reducer、接收用户插话 | 任何预测计算、任何资金/交易、任何市场价读取（盲测） |
| **API 层** `apps/web/app/api/research/*` | Next.js 路由（Serverless 函数） | 鉴权 + 配额（`consumePredictionRunQuota`）、选 driver、把引擎事件转成 SSE 帧、（新）创建 run / 持久化 / 路由插话 | 长任务本身的常驻计算（Serverless 上跑不满 12–15 分钟） |

**这张图要读出的三件事**：

1. **前端永远是无状态的薄客户端**——它只渲染、订阅、上报，不做任何计算。刷新页面靠 ③ 拉快照恢复，不靠浏览器内存。这点现有代码已经做对了一半（纯 reducer + `useResearchStream`），缺的是「刷新能恢复」。
2. **API 层（Serverless 函数）是无状态且有墙钟上限的**——这是整个改造的物理约束源头。它不能 hold 住一条 12–15 分钟的流，所以长任务的真实计算必须搬到「常驻进程」（raven-cloud / VPS orchestrator），API 层退化成「创建 run + 代理流 + 读快照」的瘦代理。
3. **真引擎（pulse 7 阶段）目前是 CLI 批处理黑盒**（`scripts/pulse-live.ts` / `services/orchestrator`），一次性产出 `pulse.json`，**不是一个能在阶段间停下来听外部输入的常驻协作服务**。这直接限制了「运行中加 context 在真引擎链上能做到什么程度」（见 7.3）。

> **诚实提示（避免画饼）**：C-end `/research` 控制台当前三条 driver 里，只有 `vps` 链路接得到真引擎，且 `vps-agent-driver.ts:53` 默认超时是 `120_000ms`（2 分钟）。换言之 **C-end 从来没真正跑过一次 12–15 分钟的真 run**——那条 12–15 分钟成本画像（见 [`docs/diagrams/forecasting-cost-profile.md`](docs/diagrams/forecasting-cost-profile.md)）来自 CLI / VPS orchestrator 实跑，不是控制台。所以「C-end 是否真要接真引擎」是优先级最高的待拍板项之一。

### 7.2 SSE 流式：进度怎么从引擎流到屏幕

**结论**：协议本身（`ResearchEvent` 判别联合）保留不动，只做三处增量；前端 reducer 几乎零改（`default` 分支已验证能吞未知事件，向后兼容老 driver）；但**传输层/解析层/重连逻辑是实打实的新代码**，不要被「reducer 几乎零改」这句话误导。

#### 现在的流式（已就绪，可复用）

- **协议**：`events.ts` 定义 11 种事件的判别联合，`encodeResearchEvent` 把每个事件编码成一帧 `event: <type>\ndata: <json>\n\n`。
- **客户端**：`use-research-stream.ts` 用 `fetch` 打开 POST、消费 `ReadableStream`、按行扫描 `startsWith("data:")` 解析、逐帧 dispatch 进 `researchReducer`（纯函数、无副作用，`state-machine.ts`）。
- **事件顺序保证**：`run.accepted` → (`stage.enter` → `stage.progress*`/`*.add*` → `stage.exit`)* → `run.conclusion` → `run.complete`；`run.notice` 任意位置；`run.error` 终止。

现有 11 种事件（全部保留）：

| 事件 | payload 关键字段 |
| --- | --- |
| `run.accepted` | `runId, eventText, driver, tier?, marketProbability, stages[]` |
| `stage.enter` / `stage.exit` | `stageId, order` / `stageId, outcome, artifactLabel?, durationMs` |
| `stage.progress` | `stageId, text`（思考旁白） |
| `evidence.add` / `model.add` / `update.add` | `evidence` / `node` / `update`（结构化产出物） |
| `run.conclusion` / `run.complete` | `conclusion` / `run: PredictionEngineRun` |
| `run.notice` / `run.error` | `level, message` / `message, code?` |

#### 三处增量改造

| 改造 | 现状 | 改成 | 风险/工作量 |
| --- | --- | --- | --- |
| **(a) 加帧序号** | `events.ts:77` 输出无 `id:` 行 | 每帧加 `id: <单调递增 seq>`，`seq` 在持久化每个事件时分配 | 改 encode + 改客户端记录 last seq；reducer 零改 |
| **(b) 新增事件类型** | 11 种 | +`run.queued`、`run.heartbeat`/`stage.heartbeat`、`context.applied`、`followup.progress`/`followup.answer`、（可选）`stage.await_input` | reducer 加 case；`default` 分支天然兼容老 driver |
| **(c) 流独立可重连** | 流挂在创建 POST 上，一断全丢 | 创建即返回 runId，流是独立的 `GET /runs/{id}/stream`，断线重连按 `Last-Event-ID` 只补发更大 seq、不重放整段 | **传输层重写**（见下方诚实说明） |

新增事件 payload（核心几个）：

| 新事件 | payload | 用途 |
| --- | --- | --- |
| `run.queued` | `{ runId, position? }` | 异步创建后排队态 |
| `run.heartbeat` | `{ seq, ts, stageId?, elapsedMs?, etaRangeSec?:[min,max] }` | 防 CDN 5 分钟静默掐断；驱动「仍在工作」指示器 |
| `context.applied` | `{ contextId, summary, affectedStageId?, affectedNodeId? }` | 插话被采纳后回流，紧跟 `update.add` 显示概率怎么变 |
| `followup.progress` / `followup.answer` | `{ followupId, text }` / `{ followupId, answerMd, refsTouched }` | 追问的针对性补充流 |

#### 心跳（heartbeat）：把「静默 5 分钟」翻译成人话

成本画像实测「研究+渲染阶段静默 5 分钟属正常」。心跳就是每 10–15 秒发一帧 `run.heartbeat`（带「当前阶段 + 已耗时 + 预计区间」），让 UI 显示一个会动的「仍在工作」指示器，而不是让用户以为死机。

**诚实底线**：心跳是改善体感，不是给慢引擎打掩护——渲染持续 >15 分钟仍按 regression 处理（见 cost-profile 约定）；并且心跳的价值兑现**依赖真长 run 接进来**（当前 mock 12 秒就跑完，心跳只跳几下看不出价值），所以心跳应在 Serverless 墙钟问题解决后、真 run 接通时一并验收。

> **诚实说明 — 「Last-Event-ID 续传」不是免费的**：SSE 标准的 Last-Event-ID 自动重连是浏览器原生 `EventSource` 的能力。但现有客户端（`use-research-stream.ts:66`）用的是 `fetch`+`ReadableStream` 手动分帧，**不是 `EventSource`**，所以这个自动机制根本不会触发。要做续传必须：改 encode 加 `id:` → 改客户端记录 last seq → 重连时手动带 `Last-Event-ID` header → 服务端按 seq 补发。`EventSource` 又不支持 POST body，所以要么自己在 fetch 流上实现往返，要么把创建/订阅彻底拆成「POST 创建 + GET 订阅」（本方案选后者）。reducer 确实几乎零改，但这句话不能掩盖传输层的重写。

### 7.3 长任务架构：异步 run + 可重连流

**核心决策（一句话）**：把「同步流式」改成「异步任务 + 可重连流」。这是本 PRD 工程量最大、且其他一切（加 context、刷新恢复、历史、分享）都依赖的前置改造。

#### 为什么必须改（而不是优化现状）

现在整条 12–15 分钟流挂在一个 POST 的生命周期上。在生产 Vercel Serverless 上：

1. **墙钟硬上限**：`vercel.json` 没配 `maxDuration`，Vercel Pro 默认 60s，单函数跑不满 12–15 分钟——长 run **物理上跑不完**。
2. **实例无状态、跨调用不共享内存**：POST 创建 run 的函数实例和 GET 订阅流的函数实例**几乎一定不是同一个**。所以「在 apps/web 进程内放 run 注册表」这个选项在 Serverless 上**根本不可用**（不是 tradeoff，是不可行）——插话会投递到错误实例，run 状态读不到。
3. **一断全丢**：用户切后台 / 网络抖动 / CDN 超时，整段流丢失且无法恢复，对长任务是致命的。

#### 改成什么（三步走的请求形态）

```
① POST /api/research/runs                  → 秒回 { runId, status:'queued' }   不阻塞 12–15 分钟
② GET  /api/research/runs/{id}/stream       → 独立订阅 SSE；可断线重连
       Header: Last-Event-ID: <seq>          （从断点续传，不重放整段）
       Query : ?replay=full|tail             （中途加入默认 full 回放完整推理链）
③ GET  /api/research/runs/{id}              → 非流式快照（刷新/历史回看/分享）
```

这一步**同时补上四个现有空白**：长任务可重连、运行中可加 context（反向通道要能让另一请求读写同一 run 的 store）、刷新即丢、无会话历史。

#### 承载位置（开工前必须拍板，不能拖到中途）

| 选项 | 可行性 | 取舍 |
| --- | --- | --- |
| ~~apps/web 进程内 run 注册表~~ | **❌ Serverless 上不可用** | 多实例不共享内存，直接排除 |
| **A. 长任务搬到常驻进程**（raven-cloud / VPS orchestrator），apps/web 退化成 Serverless 瘦代理 + 读 DB 快照 | ✅ 推荐 | raven-cloud 需先从「内存 + 同步 runner」升级成「Postgres + 异步任务队列 + SSE」 |
| **B. Vercel 支持的 background/queue 机制**（外部 worker + DB/Redis 轮询） | ✅ 可行 | 引入额外 worker 与轮询，运维面变大 |

无论选 A 还是 B，**run 状态、事件序列、seq 必须落 Postgres / Redis**（`packages/db` 已有 Postgres，但**无 runs 表，是新建 migration，不是复用**）。可重连流读 DB 回放，而不是读内存。

#### 配额收尾的隐藏坑（异步化后必须一并改）

现有并发配额（`prediction-access.ts:282`）靠 `prediction_usage_events.status='running'` 行计数，靠请求 `finally` 里的 `completePredictionUsageEvent` 收尾（`route.ts`）。**异步化后请求早就返回了，`finally` 不再覆盖整个 run 生命周期**——如果不改，`running` 计数会泄漏，`concurrentLimit=1` 的用户第二次永远被 429。

**修正**：异步 run 的状态收尾必须由**后台 worker 写 DB**，不能依赖 HTTP 请求 `finally`。另外注意：`disabled` 模式（无 `DATABASE_URL`）下 `consumePredictionRunQuota` 直接 `return {allowed:true}` 且不写库——**演示态下历史/共享 store/分享必须降级，或明确要求 `DATABASE_URL`**。

#### 加 context 的三档生效路径（诚实分级）

| 档位 | 操作 | 生效路径 | 体感 |
| --- | --- | --- | --- |
| **轻** | 贴一段话/链接当背景或候选证据 | `POST /runs/{id}/context` → 写按 runId 的共享 store → driver 在 `stage.exit` 后、下个 `stage.enter` 前读队列、采纳后发 `context.applied` + 后续 `update.add` | 输入即时被乐观回显「你说了…」，确认后变「已在[称重]阶段采纳」 |
| **中** | 忽略/降权/提权某条证据 | 纯权重调整，**前端即时重算**贝叶斯瀑布 | 秒级、0 token |
| **重** | 改判定参数（如换截止日） | 改变了「事件定义」本身，需经 `/control` pause→recompute，触发受影响节点局部重跑 | 明确等待反馈，不假装即时 |

> **诚实仲裁 — 「阶段边界采纳」在真引擎上做不到**：在 mock/replay 链上，`replay.ts` 的循环里加一个 `await drainContextQueue(stageId)` 检查点即可演示「阶段边界采纳」——可行。但真引擎（VPS / orchestrator）是一次性产出 `pulse.json` 的 CLI 黑盒（raven-cloud 的 `pulse-command` 更是 `spawn` 一个 shell 等它退出），**没有阶段间回头读队列的挂钩**。把它改成「可中断、阶段间可回灌输入的有状态服务」是 orchestrator 的重写，**不在「不重写引擎」承诺内**。因此 MVP 现实口径：**运行中加 context 仅在 mock 链可演示；真引擎链短期只做「运行后 followup 子 run」**（followup 是新建 run、不要求中断旧 run，相对现实）。

### 7.4 部署形态与对架构的硬约束

**结论**：当前生产部署是 **Vercel Serverless**（`vercel.json` `"framework":"nextjs"`，无 `maxDuration`），合入 `main` 触发 GitHub→Vercel 自动部署。这个形态决定了上面所有架构决策的边界。

| 部署链路 | 当前状态 | 对长任务的影响 |
| --- | --- | --- |
| `apps/web`（含 `/research`）→ Vercel（当前 `autopoly-pizza-spectator`，后续并入 `forecasting-agent.com`） | 自动部署 | Serverless 函数有墙钟上限，**长 run 跑不完**；mock(12s) 与本地 Node 跑得动 |
| `forecasting-agent.com`（独立 `web` 项目） | 手动部署 | 同上 |
| raven-cloud（独立 repo，Fastify:8788） | 候选常驻承载位 | 内存 store + 同步 runner + 无 SSE，需升级成 Postgres + 异步 + 流式才能承载长任务 |

**对架构的三条硬约束**：

1. **长任务不能放在 Serverless 函数里跑**——必须搬到常驻进程（7.3 选项 A/B）。这是「异步化是其他一切前置」的物理原因。
2. **心跳在 Serverless 上也受墙钟限制**——如果函数 60 秒被杀，心跳发不到第 5 帧。所以心跳真正起作用，前提是流由常驻进程（或可长连的代理）发出。
3. **盲测双闸必须在两层都设**（项目硬约束）：`POST /runs/{id}/context` 在 web 侧用 zod schema 拒绝含市场价的 context 进入生成路径；引擎侧再设一道 guard。用户贴的市场价只能进「事后与市场对比」环节，不得进预测生成（`stripPrices`）。

**apps/web 三件套验收闸门**（任何用户可见改动强制）：i18n 三语（`en`/`zh-CN`/`zh-TW` 补齐，不硬编码）；桌面 + 移动双视口截图自评（左流右文档在移动端的坍缩是新的设计工作）；本地 `pnpm --filter @autopoly/web build` 通过（用 `build` 不要用 `exec next build`，否则跳过 prebuild）。可访问性（用户视力受限）：节点展开、SVG 图表、插话栏补 `aria` + 键盘可达，关键结论保证纯文本可读。

### 7.5 契约统一（硬约束：禁双源不一致）

predict-raven 与 raven-cloud 是两套独立 schema，已漂移，必须统一到 **predict-raven 的 `PredictionEngineRun` 一套**：

| 维度 | predict-raven | raven-cloud | 统一到 |

| 7 阶段 key | `definition / query-design / evidence / weighting / model / bayes / market` | `intent_definition … output_and_market_compare` | predict-raven 命名 |

这不是「改个映射函数」，而是**跨 repo 破坏性变更**（改 raven-cloud 的 types + runners + demo + store，以及任何依赖旧 schema 的 raven-web），需定义迁移顺序：**先 predict-raven 定契约 → raven-cloud 适配 → raven-web 跟随**，必要时设双写期。

## 8. 数据契约

> **结论先行（给 PM 三句话）：**
> 1. **不重新发明数据结构。** 新契约 = 现有 `PredictionEngineRun`（已落地于 `apps/web/lib/prediction-engine-demo.ts`）+ 几个为「加 context / 追问 / 历史 / 断网重连」服务的增量字段，全部向后兼容——老 driver 不发新字段也能跑。
> 2. **三份 schema 是同一条数据流的三个切面：** 「分析报告」是最终落库与快照恢复的对象；「SSE 事件」是这份报告**流式长出来**的逐帧增量；「context 注入」是用户往里**回灌**的上行包。引用/来源 schema（`PredictionEvidence`）贯穿三者，是整份报告**可审计的最小可信单元**。

**现有字段（保留，来自 `prediction-engine-demo.ts:68`）：**

| `conclusion` | 对象 | `{ yesProbability(0–1), confidenceInterval:[lo,hi], marketProbability(可空), edge(可空), verdict }` |

| `evidence` | `PredictionEvidence[]` | 证据台账，见 8.4 |
| `model` | `PredictionModelNode[]` | 条件概率节点 A/B/C |

### 8.2 SSE 事件 Schema（线协议 = 现有 11 种 + 新增 6 种）

这是 driver（mock/api/vps）与前端 reducer 之间**唯一的契约**（`events.ts` 注释原话：this file IS the contract）。协议保持判别联合（discriminated union，靠 `type` 字段分流），新增事件走 reducer 的 `default` 分支天然向后兼容老 driver。

**现有 11 种事件（保留，来自 `events.ts:43`）。顺序保证：**

```
run.accepted → ( stage.enter → stage.progress* / *.add* → stage.exit )* → run.conclusion → run.complete
run.notice 可出现在任意位置；run.error 终止整条流。
```

| 事件 `type` | payload | 作用 |
| --- | --- | --- |
| `run.accepted` | `{ runId, eventText, driver, tier?, marketProbability, stages: ResearchStageMeta[] }` | 开场即下发 7 阶段骨架，让右栏先铺灰显空位 |
| `stage.enter` | `{ stageId, order }` | 某阶段开始 |
| `stage.progress` | `{ stageId, text }` | 思考旁白（自由文本，逐行吐） |
| `evidence.add` | `{ stageId, evidence: PredictionEvidence }` | 新增一条证据 |
| `model.add` | `{ stageId, node: PredictionModelNode }` | 新增一个条件节点 |
| `update.add` | `{ stageId, update: PredictionUpdate }` | 新增一步贝叶斯更新 |
| `stage.exit` | `{ stageId, outcome, artifactLabel?, durationMs }` | 某阶段收尾，收起成一行结论 |
| `run.conclusion` | `{ conclusion: ResearchConclusion }` | 结论卡数据（概率 + 区间 + edge + verdict） |
| `run.complete` | `{ run: PredictionEngineRun }` | 整份报告回填（终态快照） |
| `run.notice` | `{ level: "info"\|"warn", message }` | 内联提示（如「driver 未配置，已回退 mock」） |
| `run.error` | `{ message, code? }` | 致命错误，终止流 |

**新增事件（本 PRD）：**

| 新事件 `type` | payload | 作用 |
| --- | --- | --- |
| `run.queued` | `{ runId, position? }` | 异步创建后秒回，标记排队中 |
| `run.heartbeat` | `{ seq, ts, stageId?, elapsedMs?, etaRangeSec?:[min,max] }` | **心跳**：防 CDN 5 分钟静默掐断；左栏「仍在工作」指示器的数据源。每 10–15s 一帧 |
| `stage.heartbeat` | `{ stageId, seq, elapsedMs, etaRangeSec?:[min,max] }` | 阶段级心跳，可与 `run.heartbeat` 二选一 |
| `context.applied` | `{ contextId, summary, affectedStageId?, affectedNodeId? }` | 用户加的 context 在阶段边界被采纳后回流；紧跟其后的 `update.add`/`model.add` 显示概率怎么变 |
| `followup.progress` | `{ followupId, text }` | 追问的流式旁白 |
| `followup.answer` | `{ followupId, answerMd, refsTouched }` | 追问的最终回答 |
| `stage.await_input?` | `{ stageId, prompt }` | （可选）阶段间停下等用户确认，配合 `/control pause` |

**帧格式（为断线续传新增 `id:` 行）：**

```
id: <单调递增 seq>
event: <type>
data: <JSON>
<空行>
```

- `seq` 由后端**持久化每个事件时分配**（落 Postgres/Redis，不能只在内存）。
- 重连时客户端带 `Last-Event-ID`，服务端**只补发更大 seq**，不重放整段。
- ⚠️ **现状落差**：`encodeResearchEvent`（`events.ts:76`）目前只输出 `event:` + `data:`，**没有 `id:` 行**；客户端 `use-research-stream.ts` 用 `fetch`+`ReadableStream` 手动分帧、只认 `data:` 行，**不是浏览器原生 `EventSource`**——所以「Last-Event-ID 自动续传」不会自动触发，必须**在传输层 / 解析层补实现**。reducer 本身几乎零改，但别让「加个序号」这句话掩盖传输层改造。

### 8.3 Context 注入 Schema（`ContextItem` — 加 context 的核心）

用户往运行中 / 已完成的 run 里「说话」的上行数据单元。一份 `ContextItem` 既是请求体里的元素，也会沉淀进报告的 `contextLog[]`。

```ts
interface ContextItem {
  id: string;
  kind: "note" | "url" | "evidence_override" | "param_override";
  value: string;                                  // 文本 / 链接 / 覆盖说明
  stance?: "support" | "oppose" | "neutral";      // 用户主张的立场（可空）
  targetNodeId?: "A" | "B" | "C";                 // 归到哪个条件节点
  targetEvidenceId?: string;                      // 配合 evidence_override 指向某条证据
  weightHint?: number;                            // 用户建议权重 / 降权提权
  createdAtUtc: string;
}
```

**三条注入路径（由轻到重）：**

| 路径 | 入口 | 采纳时机 | 体感 |
| --- | --- | --- | --- |
| **运行前预置** | `POST /runs` 带 `context[]` | 作为高优先级输入进 query-design / evidence 阶段，标 `sourceType='用户提供'` | 直接影响整轮 |
| **运行中追加** | `POST /runs/{id}/context` | **阶段边界采纳**（`stage.exit` 后、下一个 `stage.enter` 前读队列），发 `context.applied` + 后续 `update.add` 回流；轻档不打断当前阶段，重档经 `pause → recompute` | 乐观回显「你说了…」→ 收确认后变「已在[称重]阶段采纳」 |
| **运行后** | `POST /runs/{id}/followup` | 生成**继承父 run 证据池**的子 run，只重算相关部分 | 省 token，不重跑整管线 |

> **诚实边界：** 输入即时被确认（乐观回显），**实际生效在下一个安全检查点**，绝不假装即时改写已算完的阶段。且「阶段边界回头读队列」只在 mock/replay 链上可做；真引擎（VPS/orchestrator 是一次性批处理）短期只能靠**运行后 followup 子 run** 兑现「运行中加料」的体感。

### 8.4 引用 / 来源 Schema（`PredictionEvidence` — 可审计最小单元）

这是整份报告**可审计性的最小可信单元**：把「某条新闻 / 声明」明确绑定到「拉高 / 拉低哪个条件节点多少 pp」。字段已落地（`prediction-engine-demo.ts:22`），**不动**。

```ts
interface PredictionEvidence {
  id: string;
  sourceType: string;        // 来源类别（"官方声明"/"主流媒体"/"第三方分析"…，渲染时按 locale 本地化）
  title: string;
  date: string;              // YYYY-MM-DD
  stance: "support" | "oppose" | "mixed" | "neutral";  // 立场
  weightPct: number;         // 对所挂节点的影响（±pp）
  reliability: number;       // 信度 0–1
  node: string;              // 挂在哪个条件节点（"A"|"B"|"C"）
  excerpt: string;           // 摘录
  url?: string;              // 原文链接（当前表格未渲染成可点链接，本 PRD 补上）
}
```

**`stance / weightPct / reliability / node` 这四元组是核心可审计单元**——台账按 `|weightPct|` 排序，每行能回答「这条证据支持还是反对、把哪个节点推了多少 pp、可信度多高」。本 PRD 的增量：

- 用户提供的证据/context **一律标 `sourceType='用户提供'`、`reliability` 偏低且显式展示**，绝不冒充一手核查。
- 台账每行可「忽略 / 降权 / 提权」→ 前端**即时重算**贝叶斯瀑布（秒级、0 token）。
- `url` 渲染成可点链接 + 点开看 `excerpt`/原文。

**关联节点 / 更新对象（保留）：**

| 对象 | 字段 |
| --- | --- |
| `PredictionModelNode` | `{ id:"A"\|"B"\|"C", label, probability(0–1), rationale }`（可加前端 `expanded` 位，不必入库） |
| `PredictionUpdate` | `{ label, from, to, explanation }`（贝叶斯瀑布每一步） |

### 9.2 预测引擎：概率 + 推理链 + 来源 + 结论生成

引擎输出统一为 `PredictionEngineRun`（定义见 `apps/web/lib/prediction-engine-demo.ts`），由三条 driver 中任意一条产出同一套事件流。一次完整 run 的产物按四块组织：

**(a) 概率与结论（`conclusion`）**

```
conclusion: {
  yesProbability: number,            // 0–1
  confidenceInterval: [number, number], // 80% 主观可信区间，UI 必须标注「非频率派」
  marketProbability: number | null,  // 市场隐含概率（可空；仅事后对比，见 9.10 盲测）
  edge: number | null,               // 模型 − 市场（marketProbability 为空则跳过）
  verdict: string
}
```

**(b) 推理链（7 阶段 + 条件概率树 + 贝叶斯瀑布）**

7 阶段固定流水线（`stages: PredictionStage[]`，id 见下表），每阶段带 `title/summary/detail/durationMs`：

| order | research stage id | Pulse 对应阶段 | 做什么 |
| --- | --- | --- | --- |
| 1 | `definition` | `intent_definition` | 锁定主体/截止日，标注结算判定 |
| 2 | `query-design` | `baseline_inference_search` | 拆成 2–5 个条件节点 A/B/C，生成检索 query |
| 3 | `evidence` | `evidence_collection` | 按来源类型收集 N 条证据 |
| 4 | `weighting` | `evidence_weighting` | 按一手质量/时效/交叉印证打分，分支持/反对 |
| 5 | `model` | `model_decomposition` | 建条件概率 `P(A)×P(B|A)×P(C|A,B)`（`model: PredictionModelNode[]`） |
| 6 | `bayes` | `bayesian_update` | 把证据折成有界更新（`updates: PredictionUpdate[]`，prior→posterior） |
| 7 | `market` | `output_and_market_compare` | 与市场隐含概率对比，算 edge（仅事后） |

- **条件概率树**：`model` 数组，每节点 `{ id:'A'|'B'|'C', label, probability(0-1), rationale }`。
- **贝叶斯瀑布**：`updates` 数组，每步 `{ label, from, to, explanation }`，台阶式展示 prior 如何被证据推到 posterior。

**(c) 来源（证据台账，可审计最小单元）**

`evidence: PredictionEvidence[]`，每条四元组绑定到节点，是整份报告可审计性的最小可信单元：

```
PredictionEvidence: {
  id, sourceType,          // 来源类别（官方声明/主流媒体/第三方分析…），渲染时按 locale 本地化
  title, date,             // YYYY-MM-DD
  stance: 'support'|'oppose'|'mixed'|'neutral',
  weightPct: number,       // 对某节点的 ±pp 影响
  reliability: number,     // 0–1 信度
  node: 'A'|'B'|'C',       // 挂在哪个条件节点
  excerpt, url?            // 摘录 + 原文链接
}
```

**(d) 结论生成的诚实边界**

「数字变真」目前**尚未打通**，这是引擎侧最大的真实工作量（蓝图说成「关键一笔」是低估）：

- `api-driver.ts:101` 有 `TODO(integration)`，`:210-213` 的 INTEGRATION POINT 现状是：live 模型文本只作为「旁白」叠在 `buildPredictionDemoRun()` 生成的 demo 骨架上（`splitNarration` 砍到 8 行，`api-driver.ts:195`），**概率/证据/节点数字仍是 demo 的**。
- 要让数字变真，需要：让模型严格按 JSON schema 吐 `evidence/model/conclusion` → zod 校验 → 校验失败重试/降级 → 全程不读市场价（盲测）。这是一整个「结构化推理 prompt + 输出契约 + 校验 + 失败回退」工程，不是一行接线。
- **在它打通前**：所谓「忽略某条证据→秒级 0-token 重算」只能重算 demo 数字。MVP 卖点必须诚实标注这层。

### 9.3 API 表面（7 个端点，扩展自现有单一 `/api/research/stream`）

现状只有一个端点：`POST /api/research/stream`（`route.ts`），整条 12–15 分钟流挂在这一个请求的生命周期上。拆成 7 个：

| 端点 | 作用 | 请求/响应要点 |
| --- | --- | --- |
| `POST /api/research/runs` | 创建 run，**秒回 runId**（`status=queued`），不阻塞 | body: `{ eventText(≤600), marketPrice?, tier?, locale?, context?: ContextItem[], idempotencyKey? }`；沿用现有 `consumePredictionRunQuota` 的 401/403/429 |

### 9.4 流式协议：SSE 不变，只做三处改动

线协议（`events.ts` 的 `ResearchEvent` 判别联合 + `encodeResearchEvent`/`parseResearchEvent`）**保持判别联合形态不变**，只做三件事：

1. **加 `id:` 序号**：现在 `encodeResearchEvent`（`events.ts:76`）输出 `event:<type>\ndata:<json>\n\n`，**无 id 行**。新增 `id:<单调递增 seq>`。seq 由后端持久化每个事件时分配。
2. **新增 4–6 类事件**（reducer 加对应 `case`，`default` 分支保证老 VPS driver 向后兼容）：
   - `run.queued { runId, position? }`
   - `run.heartbeat { seq, ts, stageId?, elapsedMs?, etaRangeSec?:[min,max] }` — 心跳，UI「仍在工作」数据源
   - `stage.heartbeat { stageId, seq, elapsedMs, etaRangeSec? }` — 阶段级（可与 run 级二选一）
   - `context.applied { contextId, summary, affectedStageId?, affectedNodeId? }` — 紧跟 `update.add/model.add` 显示概率怎么变
   - `followup.progress { followupId, text }` / `followup.answer { followupId, answerMd, refsTouched }`
   - （可选）`stage.await_input { stageId, prompt }` — 配 `/control pause`
3. **流独立可重连**：流不再挂在创建请求上。

**事件顺序保证**（沿用 `events.ts:38-42` 既有契约 + 新增）：
`run.queued? → run.accepted → (stage.enter → stage.progress*/heartbeat*/*.add* → stage.exit)* → run.conclusion → run.complete`；`run.notice/heartbeat` 任意位置；`run.error` 终止。

⚠️ **续传不是「加个序号」就完事**（蓝图说「reducer 几乎零改」对，但别被这句话掩盖传输层重写）：客户端 `use-research-stream.ts:97` 只认 `line.startsWith("data:")`，用的是 `fetch`+`getReader`（`:84`）**不是浏览器原生 `EventSource`**——所以「`Last-Event-ID` 自动续传」这个 SSE 标准机制**不会触发**（那是 `EventSource` 的能力）。要续传必须自己实现：客户端记录 last seq → 重连时手动带 `Last-Event-ID` header → 服务端按 seq 只补发更大序号。reducer 几乎零改属实，但传输层/解析层/重连逻辑是实打实的新代码。

### 9.5 运行模式：local / VPS / demo（三 driver 热切换）

三条现成 driver 由 `RESEARCH_DRIVER` env 热切换，都吐同一套事件：

| driver | env | 现状 | 用途 |
| --- | --- | --- | --- |
| `mock`（demo） | `RESEARCH_DRIVER=mock` | 确定性 demo，`buildPredictionDemoRun` + `replayRun`，速度由 `RESEARCH_MOCK_SPEED` 控（默认 0.9，≈12–14s 走完） | UI/QA + 兜底；任何 live driver 未配置时自动 fallback 并发 `run.notice` |
| `api`（Chain B / local 直连模型） | `RESEARCH_DRIVER=api` + `RESEARCH_API_LIVE=true` | 直连 Anthropic/OpenAI，当前只把模型文本当旁白叠 demo 骨架（见 9.2(d)） | 本地/直连推理；「数字变真」的接线点 |
| `vps`（Chain A） | `RESEARCH_DRIVER=vps` | POST 到 VPS，回 SSE 直通或 JSON 本地 replay；背后是 `services/orchestrator` 的 pulse 7 阶段流 | 生产真引擎链路 |

⚠️ **运行中「阶段边界采纳」在真引擎链上短期做不到**：`replay.ts:164` 的 `replayRun` 是单向自驱动 `for (const stage of orderedStages)` 循环，中间只有 `sleep` 和 `signal`（只能 abort，不能注入）。在 mock/replay 路径上可加 `await drainContextQueue(stageId)` 检查点——这部分可行；但真引擎（VPS/orchestrator）是 CLI 批处理一次性产 `pulse.json`，不是能在阶段间停下听外部输入的常驻服务，改造它属于 orchestrator 重写、不在「不重写引擎」承诺内。**MVP 诚实口径：运行中加 context 仅在 mock 链可演示；真引擎链上短期只做「运行后 followup 子 run」**（followup 是新建 run，不要求中断旧 run，相对现实）。

### 9.6 长任务架构：异步 run + 可重连流（最核心、必须最先做）

🔴 **这是蓝图判断错误、必须纠正的一处**。蓝图假设「现在整条流挂在一个 POST 上」是个可保留的同步流，并把异步化排在 Phase 2。实际：

- **生产部署在 Vercel Serverless**：`vercel.json` 为 `{ "framework": "nextjs" }`，**无 `maxDuration`**；`route.ts:20` 为 `runtime="nodejs"`。CLAUDE.md 明确「合入 main 触发 GitHub→Vercel 自动部署」。
- **后果**：(a) Serverless 函数有墙钟硬上限（Pro 默认未配置即 60s），现有 12–15 分钟的真 run **在 Vercel 上根本跑不完**，只有 mock(12–14s) 和本地 Node 跑得动；(b) 函数实例无状态、跨调用不共享内存，POST 创建的 run 和 GET 订阅的流**几乎一定落在不同实例**——「apps/web 进程内 run 注册表」在 Serverless 上**根本不可用，不是 tradeoff**。

**正确架构决策**：把同步流式改成异步任务 + 可重连流：

```
POST /api/research/runs            → 秒回 runId（status=queued），任务异步跑
GET  /api/research/runs/{id}/stream → 独立订阅，断网靠 Last-Event-ID 续传，
                                      中途加入默认 full 回放完整推理链
GET  /api/research/runs/{id}        → 拉快照（刷新/历史/分享）
```

这一步同时补上「刷新即丢、无会话历史」的空白，也是反向通道（另一请求要能读写同一 run 的 store）的前提。

**承载位置（前置阻塞决策，必须用户拍板，且排除「apps/web 进程内」）**，真正可行两条路：
1. 长任务搬到**常驻进程**（raven-cloud / VPS orchestrator），apps/web 只做 Serverless 代理 + 读 DB 快照；
2. 用 Vercel 支持的 background/queue 机制（外部 worker + DB/Redis 轮询）。

run 状态、事件序列、seq **必须落 Postgres/Redis**（`packages/db` 已有 Postgres，但**无 runs 表，是新建 migration，不是复用**）。可重连流读 DB 回放，不读内存。

### 9.7 数据契约：复用 `PredictionEngineRun` + 增量字段

不重新发明结构。新契约 = 现有 `PredictionEngineRun` + 为「加 context/追问/历史/重连」服务的字段，保持向后兼容。

**新增字段**（叠在现有 `id/eventText/conclusion/stages/evidence/model/updates/limitations/archiveLinks` 之上）：


**ContextItem（加 context 核心，新增）**：

三种注入路径：运行前预置（`POST /runs` 带 `context[]`，标 `sourceType='用户提供'`）；运行中追加（`POST /runs/{id}/context`，阶段边界吸收发 `context.applied` + `update.add`）；运行后（走 followup 生成继承父 run 证据池的子 run）。

🔴 **契约统一是独立的跨 repo 工作项（硬约束，禁双源不一致）**：predict-raven 与 raven-cloud 两套 schema 已漂移——stance（predict-raven `support/oppose/mixed/neutral` vs raven-cloud `supports/weakens/mixed/context`）、stage key（`definition/query-design/…/market` vs `intent_definition/…/output_and_market_compare`）。统一到 predict-raven 的 `PredictionEngineRun` 一套，意味着改 raven-cloud 的 types/runners/store 及 raven-web，需定义迁移顺序（先 predict-raven 定契约 → raven-cloud 适配 → raven-web 跟随）+ 双写期，不是改个映射函数。

### 9.8 信息源接入与引用

- **现有来源**：Web 搜索仅 DuckDuckGo HTML 解析（`services/orchestrator/src/pulse/web-search.ts`，每候选 4 query×4 结果）+ Polymarket 评论/规则/订单簿。Twitter/X、Reddit、Telegram、军事地图、区域官方源未集成。
- **引用模型**：每条证据带 `url`（原文链接）+ `excerpt`（摘录）+ `sourceType` + `reliability`。决策侧（Pulse）另有 `scoreSourceQuality()`（0–100）和 `sourceCoverage()`（权威/市场结构/事件状态/基准/反证）。
- **C-end 引用渲染缺口（待补）**：现 `EvidenceLedger` 表格**未把 `url` 渲染成可点链接**（字段存在但只读）。第一层纯前端交互应补：url 可点 + 每行可「忽略/降权/提权」即时重算 + 节点/来源/局限可展开。
- **用户提供的 context 一律标 `sourceType='用户提供'`、`reliability` 偏低且显式展示**，绝不冒充一手核查。

### 9.9 缓存与增量重算

实测开销（引用 `docs/diagrams/forecasting-cost-profile.md`，每 session 结束按约定追加 `runtime-artifacts/pulse-live-cost-ledger/`）：一次 run ≈ **12–15 分钟、约 40–50k 输入 + 5k 输出 token，渲染占 95%，静默 5 分钟内正常**。⚠️ 这条画像来自 CLI/orchestrator 实跑，**C-end 三 driver 现在没有任何一条会让用户等 12–15 分钟**（mock 12 秒走完，VPS driver 120s 就超时）——心跳要解决的「假死体感」在当前 C-end 路径上还不存在，其价值兑现依赖真 run 接进来（见 9.11）。

**三层缓存**：

| 层 | key | 命中行为 |
| --- | --- | --- |
| 整 run 缓存 | `hash(eventText + tier + locale + marketPrice)` | 24h 内完成的 run 直接回放（mock 已用 `hashText` 做确定性 key） |
| 证据池缓存 | `query + 日期窗口` | web-search 缓存数小时；追问/加 context 复用父 run 证据池，只补差量 |
| prompt caching | 证据账本 + 阶段说明前缀 | 走模型侧前缀缓存 |

**增量重算分级（诚实口径）**：

| 档 | 操作 | 成本 |
| --- | --- | --- |
| 证据 override（忽略/降权某条） | 纯权重调整，前端重算贝叶斯瀑布 | 秒级、0 LLM |
| 轻档加 note/url | 追加一条 evidence + 重算 `buildUpdates` | 约 1 次便宜 LLM、秒级 |
| param_override（如换截止日） | 改变事件定义，部分重跑受影响节点 | 部分 LLM |
| whatif 追问 | 父 run 证据池上只重算条件树 | 中等 |

tier 策略：首次生成可上 `skuld`，追问/加 context 默认降到 `verdandi`/`urd` 控成本。**>15 分钟持续渲染按 regression 处理，不放宽容忍度**——心跳是改善体感，不是给慢引擎打掩护。

### 9.10 超时与心跳

- **现有超时**：VPS driver 默认 `120_000ms`（2 分钟，`vps-agent-driver.ts:53`，`RESEARCH_VPS_TIMEOUT_MS` 可覆盖）——但蓝图自己说一轮 12–15 分钟，**这个 2 分钟超时和真 run 自相矛盾**，必须提到 ≥18min。`/api/prediction-engine/run` 端 120s（`PREDICTION_ENGINE_API_TIMEOUT_MS`）。两者均硬失败、无重试。
- **心跳（防 CDN 静默掐断 + 防假死体感）**：`events.ts` 加 `run.heartbeat`/`stage.heartbeat`，每 10–15 秒发一帧（带「当前阶段 + 已耗时 + 预计区间」），reducer 加一个 `case`，`replay.ts` 在 `sleep` 间穿插发，UI 显示会动的「仍在工作」。
- ⚠️ **心跳在 Serverless 上同样受墙钟限制**：若函数 60 秒被杀，心跳发不到第 5 帧——所以心跳的价值同样依赖 9.6 的异步化先落地（长任务搬到常驻进程后心跳才有意义）。

### 9.11 与 Pulse / forecast 流程复用

C-end research 7 stage 与 Pulse 7 阶段**一一对应**（仅 id 命名不同，见 9.2 表）。复用路径：

- **Pulse 引擎产物 → research 事件流**：需一个适配器把 `PulseSnapshot` / `recommendation.json`（`services/orchestrator/src/pulse/full-pulse.ts`、`stage-flow.ts`）翻成 `PredictionEngineRun`。其中 `model`/`updates` 在 Pulse 里目前是**自由文本**（stage 4–6 仅 `partial`），补成类型化对象是引擎侧最大真实工作量。
- **VPS driver 即复用入口**：`RESEARCH_DRIVER=vps` 时 POST 到 VPS，背后就是 `services/orchestrator` 的 pulse 流；回 SSE 直通或 JSON 本地 replay（`vps-agent-driver.ts:123-124` 按 content-type 分流）。
- **盲测边界共用**：Pulse 侧的 `stripPrices`（`scripts/world-cup/`）与 C-end 生成路径共享同一约束——预测生成不读市场价。
- **隔离要求**：⚠️ Pulse 是真钱实盘路径（`forecast:live` 不可逆下单）。C-end research 必须与交易执行器**物理隔离**——research 只读引擎产物，**绝不触发 Pulse 的执行层**（raven-cloud 的 `pulse_command` runner 默认 regex 拦 `pulse:live`/`--trade`/`AUTOPOLY_EXECUTION_MODE=live`，须保留并加固）。

### 9.12 安全与盲测双闸

- **盲测双闸（2026-06-11/19 用户决定）**：预测**生成**环节不得读市场价/隐含概率。在 `zod` schema + 服务端 guard 强制：含市场价的 `context` 在生成路径**必须拒绝**，只允许进事后对比（`/world-cup/performance` 那类基准评测）。web 校验层 + 引擎层双闸。
- **用户 context 防滥用**：URL 抓取设白名单 + 超时；`note` 走注入检测（防恶意 prompt 当 context 喂进模型）；一律标 `sourceType='用户提供'` + 低 `reliability` + 显式展示。
- **配额收尾必须改后台写（异步化新增风险）**：现 `consumePredictionRunQuota` 靠 `predictionUsageEvents.status='running'` 计并发（`prediction-access.ts:130,282`），靠 `completePredictionUsageEvent` 在 HTTP 请求 `finally` 收尾（`route.ts:123`）。异步后请求早返回、用户断连 → `complete` 不保证写回 → `running` 计数泄漏 → `concurrentLimit=1` 的用户第二次永远被 429。**必须由后台 worker 写 DB**。另：`disabled` 模式（无 `DATABASE_URL`）下 `consumePredictionRunQuota` 直接 `return {allowed:true}`（`prediction-access.ts:259-260`）不写库——演示态下配额/历史/共享 store 全空，历史/分享须降级或明确要求 `DATABASE_URL`。
- **私钥/env 不外泄**；可追溯归档：`contextLog` + `costActual` 写入归档与 cost-ledger。

### 9.13 配额与访问（需用户拍板）

现配额按「每 run」计：`PREDICTION_DAILY_RUN_LIMIT=5` / `PREDICTION_MONTHLY_RUN_LIMIT=50` / `PREDICTION_CONCURRENT_RUN_LIMIT=1`（`prediction-access.ts`），admin 可 `PREDICTION_ADMIN_BYPASS_QUOTA` 绕过。

- **冲突**：对话式产品追问频繁，「每 run 计费」会被两次对话耗尽。须**重定义计费单位**（按会话？整轮 vs 局部重跑分级？）——属产品策略，agent 不擅自定。
- **异步 + 并发 1 的副作用**：用户可离开再回来看（异步化的好处），但配额收尾不改后台写就会泄漏（见 9.12）。

### 9.14 后端落地分阶段与验收

🔴 **蓝图的 Phase 顺序（心跳 → 纯前端交互 → 异步化）前后倒置**。正确依赖序：

| Phase | 内容 | 验收标准（非「ready/done」） |
| --- | --- | --- |
| **P0 前置决策** | 定承载位置（排除 apps/web 进程内）+ 建 runs 持久化 migration（`packages/db` 新表） | 用户拍板承载位置；migration 可建表、可写 run/event/seq |

**apps/web 三件套门禁（每个触及用户可见页的 Phase 强制）**：i18n 三语（`en`/`zh-CN`/`zh-TW`）补齐 + 桌面/移动双视口自评（双栏在移动端坍缩是新设计工作）+ 本地 `pnpm --filter @autopoly/web build` 通过（用 `build` 不用 `exec next build`）。可访问性（用户视力受限）：节点展开、SVG 图表、插话栏补 `aria` + 键盘可达，关键结论保证纯文本可读。

> 结论先行（给 PM 三句话）：
> 1. **认证与邀请码两件已经在生产代码里跑通**——OIDC 登录（`apps/web/auth.ts`）+ 邀请码激活（`acceptInviteForCurrentUser`）+ 日/月/并发三维配额（`consumePredictionRunQuota`）都已实现并落库，本章大部分是「沿用 + 收口」，不是从零造。

### 10.2 认证：OIDC / Auth.js

**现在怎么工作（一句话）**：用 NextAuth.js（Auth.js v5）+ 单一 OIDC provider，登录后把 OIDC 的 `issuer + subject` 当成用户唯一身份，落到 `app_users` 表。**不支持** GitHub/Google 这类社交登录，只认标准 OIDC（如 Auth0、Keycloak、企业 SSO）。

**配置（5 个环境变量，缺一不可）**——来自 `auth.ts` 与 `.env.example:26-32`：

| Env | 含义 | 默认 |
| --- | --- | --- |
| `AUTH_SECRET` | JWT 会话签名密钥（生产必填） | 空 |
| `OIDC_ISSUER` | OIDC 颁发者 URL | 空 |
| `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` | 客户端凭据 | 空 |
| `OIDC_SCOPE` | 申请的 scope | `openid email profile` |
| `OIDC_PROVIDER_NAME` | 登录按钮显示名 | `OpenID` |
| `AUTH_TRUST_HOST` | 是否信任反代 Host | `true`（设 `false` 关闭） |

**身份模型（`app_users` 表，`schema.ts:149`）**：

- 唯一键：`UNIQUE(oidcIssuer, oidcSubject)`——同一人换邮箱仍是同一账号。
- `role`：`admin | user`，由 `PREDICTION_ADMIN_EMAILS`（逗号分隔邮箱、大小写不敏感）决定。注意：**admin 一经设置不会被自动降级**（upsert 时用 `case when role='admin' then role else ...`，见 `prediction-access.ts:189`），降级须直接改库。
- `status`：`pending_invite | active | suspended` 三态。

**JWT 会话**：无服务端 session 存储，token 里存 `oidcIssuer` + `oidcSubject`，支持多 issuer 环境（`auth.ts:52-65`）。

**6 种访问态（`PredictionAccessMode`，`prediction-access.ts:13`）**——前端据此决定显示登录/邀请/可用界面：

| mode | 含义 | API 返回 |
| --- | --- | --- |
| `disabled` | 未配 auth，演示模式开放（无 `DATABASE_URL` 或未配 OIDC，且 `PREDICTION_AUTH_REQUIRED=false`） | 200 放行 |
| `setup_missing` | auth 被要求但配置不全 | 503 |
| `unauthenticated` | 已配置但未登录 | 401 + `signInUrl` |
| `pending_invite` | 已登录但未激活 | 403 + `inviteUrl=/invite` |
| `suspended` | 账户被禁 | 403 |
| `ready` | 完全激活，附 `quota` | 200 |

**给活报告控制台的影响**：异步化后，「创建 run（POST /runs）」这一步沿用 `consumePredictionRunQuota` 的 401/403/429 即可；但「订阅流（GET /runs/{id}/stream）」「拉快照（GET /runs/{id}）」也要做**同一用户归属校验**（只能看自己的 run，admin 可看全部）——这是现有单端点没有的新校验点。

### 10.3 邀请码

**现在怎么工作（一句话）**：管理员用脚本生成一串 `rvn-xxxx` 邀请码（库里只存 SHA256 哈希，不存明文），用户在 `/invite` 页提交，校验通过即把账号从 `pending_invite` 翻成 `active`。

**生成（`scripts/prediction-invite.ts`）**：

```
tsx scripts/prediction-invite.ts \
  --max-uses 5 \
  --domain example.com \
  --expires-at 2026-12-31T23:59:59Z \
  --label "WC beta wave 1"
```

- 码格式：`rvn-{base64url(12 bytes)}`（不传 `--code` 则随机生成）。
- 落到 `invite_codes` 表（`schema.ts:165`）：`codeHash`(SHA256, UNIQUE)、`maxUses`(默认 1)、`usedCount`、`allowedEmailDomain`(可选)、`expiresAt`(可选)、`status`(默认 `active`)。

**核销流程（`acceptInviteForCurrentUser`，`prediction-access.ts:317`）**——校验顺序：

1. 已登录且账号存在；已是 `active` 直接返回 ok（幂等）。
2. 码长度 ≥ 6。
3. 哈希命中且 `status='active'`。
4. 未过期（`expiresAt > now`）。
5. `usedCount < maxUses`。
6. 若设了 `allowedEmailDomain`，用户邮箱域名须匹配。
7. 通过 → `usedCount + 1` + 用户 `status='active'` + 写 `activatedAt`。

**自动激活旁路（不用邀请码也能进的两种情况，`prediction-access-rules.ts:36`）**：

- `PREDICTION_INVITE_REQUIRED=false` → 所有登录用户自动激活（开放注册）。
- 邮箱域名命中 `PREDICTION_AUTO_ACTIVATE_EMAIL_DOMAINS`（逗号分隔）→ 自动激活（适合公司内部域名）。
- admin 邮箱永远自动激活。

**已知缺口（不阻塞 MVP，列出供拍板）**：

- 邀请码无「单用户限领一次」约束——同一用户可重复用同一码直到 `maxUses` 用尽。
- 过期的码不会自动把 `status` 标成 `expired`，仍靠 `expiresAt` 实时判断。
- 无管理后台 UI，生成/查看靠脚本 + 直接查库。

### 10.4 配额（日 / 月 / 并发）

**现在怎么工作（一句话）**：每次发起预测前调 `consumePredictionRunQuota`，按 UTC 时段检查日/月/并发三道闸，任一超限返回 **429**；通过则在 `prediction_usage_events` 表插一条 `status='running'`，跑完调 `completePredictionUsageEvent` 翻成 `complete/failed`。

**三维配额（`.env.example:37-40`，可调）**：

| 维度 | Env | 默认 | 计数口径 |
| --- | --- | --- | --- |
| 日 | `PREDICTION_DAILY_RUN_LIMIT` | 5 | UTC 当天 `startedAt` 起的事件数 |
| 月 | `PREDICTION_MONTHLY_RUN_LIMIT` | 50 | UTC 当月 1 日起的事件数 |
| 并发 | `PREDICTION_CONCURRENT_RUN_LIMIT` | 1 | 当前 `status='running'` 的行数 |

- 设为 `0` 或非正数 → 该维度判为 `null`（无限制，`readLimitEnv:66`）。
- 重置点：UTC 00:00（`dayStart`/`monthStart` 用 `Date.UTC`）。
- **admin 绕过**：`role='admin'` 且 `PREDICTION_ADMIN_BYPASS_QUOTA=true`（默认）→ 三维全设 `null`，`bypassed=true`。
- 拒绝码：日超限/月超限/并发超限都返回 **429** + 各自的 error message。

**`PredictionQuotaSummary` 接口（`prediction-access.ts:29`）**——前端配额徽标的数据源：

```
{ dailyLimit, dailyUsed, monthlyLimit, monthlyUsed,
  concurrentLimit, running, bypassed }
```

**🔴 异步化必修：配额收尾不能再靠 HTTP 请求生命周期**

现状：`running → complete` 的翻转发生在请求 `finally`（同步流挂在一个 POST 上时成立）。活报告控制台改成**异步 run**（POST 秒回 runId，引擎在后台跑 12–15 分钟，用户可随时断开/切后台）后：

- 请求早已返回，`finally` 里没有也不该写 `complete`；
- 后果：`prediction_usage_events` 里 `running` 行永远不收尾 → `concurrentLimit=1` 的用户**第二次永远 429**。

**修正**：异步 run 的状态收尾必须由**后台 worker / run 完成回调写库**，而不是 HTTP `finally`。并发计数改为「按 run 真实终态」而非「按请求是否还连着」。这是异步化（见架构章节）的连带必修项，验收标准之一是：**用户发起 run 后立即关闭浏览器，run 完成时 `running` 计数必须归零**。

**演示态的诚实标注**：无 `DATABASE_URL` 时进 `disabled` 模式，`consumePredictionRunQuota` 直接 `{allowed:true}` 放行（`:259`），**完全不写 `prediction_usage_events`**——意味着本地/演示态下配额、历史、共享 store 全是空的。历史/分享/共享 run store 这些异步化新功能，**在 disabled 模式下必须降级或明确要求 `DATABASE_URL`**。

**已知缺口**：

- 仅日/月/并发三维，无「周」或自定义窗口。
- 无 rate limiting——配额检查通过后理论上 1 秒内可连发多次（异步化 + DB 并发计数后风险下降，但仍建议补一道轻量节流）。
- 无审计导出接口，用量分析靠直接查 `prediction_usage_events`。

### 10.5 Tier（访问档 + 推理档）

| 层 | 现状 | 字段 / 位置 | 作用 |

### 10.6 计费占位

**结论先行**：MVP **不必接真支付**，但必须先把「计费单位」定清楚，否则会和活报告产品的对话频率直接冲突。

**核心冲突（来自架构章节，必须在这里拍板）**：现在按「每个 run」计费（日 5 次）。活报告控制台支持**追问（followup）**和**运行中加 context**——一次完整分析 + 两三轮追问，就把一天的 5 次额度耗光。**「每 run 计费」对一个对话式产品不成立。**

**待拍板的计费单位选项**：

| 选项 | 计费单位 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A（现状） | 每个 run（含 followup） | 实现零改 | 对话两轮就耗尽，体验差 |
| B（建议） | 整轮 vs 局部重算分级：首次完整 run 计 1 次；followup / 加 context 触发的**局部重算**计 0 或按 token 折算 | 贴合对话产品 | 需在计费层区分 run 类型 |
| C | 按「会话（session）」计：一份活报告 + 其下所有追问算一个计费单位 | 最贴近用户心智 | 须引入 session 概念与封顶 |

建议默认走 **B**：首次生成扣 1 个 run 额度；followup / 加 context 走父 run 证据池的子 run，**不单独扣 run 额度**，仅累计 token 成本（成本画像见成本章节，约 40–50k in / 5k out per 首轮）。具体由用户确认。

**计费占位的最小落地（不接支付也能做）**：

- `prediction_usage_events` 已有 `action` / `backendSource` / `metadata` 字段，可直接承载计费维度——例如 `action` 扩展出 `prediction_followup` / `prediction_recompute` 以区分计费档，`metadata` 写入 token 用量与 tier，**无需新表即可开始记账**。
- 真实成本写入约定：每次 live run 的实测开销追加进成本台账（成本章节约定的 `cost-ledger`），计费规则等真实成本曲线稳定后再定价。
- **暂不做**：真支付集成、发票、退款——列为 tier 分档拍板后的后续阶段。

## 11. 非功能需求

> 这一章管的是"不直接产出新功能、但决定产品能不能上线、敢不敢交给用户用"的硬指标：跑多久、会不会假死、断网了怎么办、出问题能不能查、中英文能不能切、用户贴的东西安不安全、给出的概率敢不敢让人当回事。
>
> **先给结论（PM 三句话）：** (1) 一次预测的真实耗时是 **12–15 分钟**，95% 花在渲染上——这是实测、不是估计；(2) 当前 C-end `/research` 走的是 **Vercel Serverless**（`apps/web/vercel.json` 只有 `framework: nextjs`，**没配 `maxDuration`**），单函数有墙钟硬上限，**真 12–15 分钟的 run 在现部署形态下跑不完**，所以"可靠性"这一节的第一条不是 SLA 数字，而是"承载位置必须先换到常驻进程"；(3) 盲测边界、可信免责、可访问性都是**验收闸门**，不达标不合并，不是"以后再补"。

### 11.1 延迟与成本画像（以实测为准，不靠传闻）

数据全部来自 [`docs/diagrams/forecasting-cost-profile.md`](docs/diagrams/forecasting-cost-profile.md)（最后更新 2026-06-12，n=3 完整实盘 run）。**任何新数字必须按该文档约定追加 CSV 到 `runtime-artifacts/pulse-live-cost-ledger/`，不得凭印象改这张表。**

| 阶段 | 实测耗时 | token | 备注 |
| --- | --- | --- | --- |
| geoblock / 持仓读取 / 下单门探针 | 各 1–2s | 0 | 探针合计 < 5s |
| **研究 + 渲染（主体）** | **719–750s（约 12 分钟）** | **每轮 ~41–42k in + ~5k out** | 占整轮 **~95%**；渲染期静默 0 字节 **5+ 分钟属正常**，内部 timeout 30 分钟 |
| 决策解析 + 风控裁剪 + 下单 | 秒级 | 0 | C-end 不涉及下单，仅生成路径相关 |

**派生指标（写进验收）：**

- **单轮预算**：12–15 分钟、~50k token（~41–42k in + ~5k out）。连跑 3 轮约 1 小时。
- **慢点唯一定位在渲染**：优化方向是 typed pipeline / 模板瘦身（见 11.6 引擎映射），不在探针和执行。
- **静默 ≠ 失败**：0 字节挂 5 分钟以内不要判死；这正是 11.2 心跳要翻译的"沉默"。
- **回归红线（硬约束，不放宽）**：渲染**持续突破 15 分钟**视为性能回归，**记 issue 而不是调高容忍度**。心跳只改善体感，不给慢引擎打掩护。

**诚实提示（必须写给用户/PM 看）：** 上表的 12–15 分钟来自 **CLI / VPS orchestrator 实跑**。当前 C-end `/research` 三条 driver 里：

| driver | 实际耗时 | 数字真假 |
| --- | --- | --- |
| `mock`（`replay.ts` 走完） | **12–14 秒** | 确定性 demo 数字 |
| `api`（`api-driver.ts`，Chain B） | 数秒（仅旁白叠在 demo 骨架） | 数字仍是 `buildPredictionDemoRun` 生成 |
| `vps`（`vps-agent-driver.ts`，Chain A） | **120s 即超时**（`RESEARCH_VPS_TIMEOUT_MS` 默认 `120_000`，见 `vps-agent-driver.ts:53`） | 真引擎，但当前接不满 |

也就是说：**C-end 目前从没真正跑过一次 12–15 分钟的真 run**。这直接决定了 11.2 的可靠性设计和 11.6 的引擎打通优先级——心跳和异步化要解决的问题，得先让真 run 接得进来才会出现。

### 11.2 可靠性

#### 11.2.1 头号风险：现部署形态承载不了长任务

| 现状（已核验） | 影响 |
| --- | --- |
| `route.ts:20` `export const runtime = "nodejs"` + `:21` `force-dynamic`，部署经 `vercel.json`（无 `maxDuration`） | Serverless 单函数有墙钟硬上限（Pro 默认 60s），**12–15 分钟的真 run 跑不完** |
| Serverless 函数实例无状态、跨调用不共享内存 | POST 创建的 run 与 GET 订阅的流**大概率落在不同实例**，进程内 store 必然投递到错误实例 |

**结论**：异步化**不是**"主要工程但有现成地基"的增量，而是**长任务承载层从零搭建**。"先在 apps/web 出可用版"这条路在 Serverless 上**走不通**——必须先拍板承载位置（见 11.6 与待拍板项）。可行的两条路：

1. 长任务搬到**常驻进程**（raven-cloud / VPS orchestrator），apps/web 只做 Serverless 代理 + 读 DB 快照；
2. 用 Vercel 支持的 background/queue 机制（外部 worker + DB/Redis 轮询）。

#### 11.2.2 可靠性目标（待承载位置定稿后填 SLA 数值）

| 维度 | 目标 | 实现要点 |
| --- | --- | --- |
| **断线重连** | 用户切后台 / 网络抖动 / CDN 超时后，重连能**从断点续传**，不重放整段、不丢已算结果 | SSE 每帧加 `id:<单调递增 seq>`；重连按 `Last-Event-ID` 只补发更大 seq。**注意**：现 `use-research-stream.ts:97` 是 `fetch`+`ReadableStream` 手动分帧、只认 `data:` 行、**不是原生 `EventSource`**，所以 Last-Event-ID 自动续传**不会触发**——需自己实现往返。续传 = 传输层/解析层新代码，**reducer 几乎零改**（`state-machine.ts:182` `default` 分支已向后兼容未知事件，已核验）。 |
| **刷新/历史恢复** | 刷新页面、历史回看、分享链接都能拉到完整推理链 | `GET /api/research/runs/{id}` 拉快照；run 状态、事件序列、seq 落 Postgres（`packages/db` 现有 Postgres，但**无 runs 表**，是新建 migration，不是复用） |
| **驱动降级** | 真引擎不可用时不硬崩 | 沿用现有 `DriverNotConfiguredError` → 透明 fallback 到 `mock` + `run.notice(warn)`（已实现） |
| **运行中假死防护** | 静默 5 分钟不让用户以为死机 | 新增 `run.heartbeat` / `stage.heartbeat`，每 10–15s 一帧（带"当前阶段 + 已耗时 + 预计区间"），reducer 加 case，UI 显示会动的"仍在工作"。**依赖**：心跳的价值兑现取决于真长 run 接进来——在 mock 的 12 秒里只跳几下看不出价值（见 11.1 诚实提示） |

#### 11.2.3 配额收尾的可靠性陷阱（异步化引入）

现并发配额（`prediction-access.ts:282`）靠 `predictionUsageEvents.status='running'` 行计数，靠 `completePredictionUsageEvent`（`prediction-access.ts:297`）在请求 `finally` 里收尾。**异步化后请求早已返回**，run 还在后台跑——若收尾仍挂在 HTTP 生命周期上，`running` 计数会**泄漏**，`concurrentLimit=1` 的用户**第二次永远 429**。

**要求**：异步 run 的状态收尾**必须由后台 worker 写 DB**，不依赖 HTTP `finally`。另：`disabled` 模式（无 `DATABASE_URL`，`prediction-access.ts:259` 直接 `return {allowed:true}`）下**不写 `predictionUsageEvents`**——历史 / 共享 store / 分享在演示态必须降级或明确要求 `DATABASE_URL`。

### 11.6 可信与免责

预测产品给出的是概率，不是承诺；信任建立在"算法可审计 + 边界说清楚 + 不冒充确定性"。

| 要求 | 落实 |

## 12. 成功指标

> 先说结论：这个产品的成败由**两类完全不同的指标**决定，不要混在一张表里看。
> - **预测准不准**（校准 / 命中）——这是产品的"真本事"，但**只能事后验证**，且必须在**盲测边界**内做（生成时不读市场价）。已经有现成实现：`scripts/world-cup/lib/performance.ts` 已经在算 Brier 技巧分、ECE、最佳预测命中、Mock PNL，C 端只是把同一套搬过来。
> - **产品好不好用 / 值不值这个钱**——参与/留存、决策采纳、单次成本。这是判断"活报告控制台"这套交互值不值得做的依据，跟预测准不准是两码事。
>
> 下面每一节都给出：**指标定义 → 取数来源（真实字段/文件）→ 目标值（北极星 / 及格线）→ 注意事项**。目标值是建议默认，需用户拍板的已标注。

### 12.0 指标总览（北极星 + 护栏）

| 类别 | 北极星指标（追求变好） | 护栏指标（不许变坏） |
| --- | --- | --- |
| 校准与准确 | Brier 技巧分 `bssPct` > 0（赢过市场） | ECE `ecePct` ≤ 10pp（别系统性过自信） |
| 决策有用 | 决策采纳率（用户看完后真的动作） | 误导率 = 0（高置信结论事后被证错的占比） |
| 参与/留存 | 周活跃用户完成 ≥1 次完整 run | 中途放弃率（run 跑到一半离开）< 25% |
| 成本/单次 | 单次完整成本（token + 墙钟）持平或下降 | 渲染 > 15 分钟持续出现 = regression（不放宽容忍度） |

> **一句话排序**：先保校准（产品立身之本）→ 再看决策采纳（有没有用）→ 最后压成本（划不划算）。参与/留存是放大器，准和有用之前，留存没意义。

### 12.1 校准（Brier / ECE）—— 预测到底准不准

**这一节回答的问题**：我们吐出来的概率，是不是言行一致？说"70% 会发生"的那批事件，事后真有约 70% 发生了吗？而且——我们比直接抄市场价**强在哪**？

**关键诚实前提（盲测边界）**：校准评测是**事后基准评测**，发生在预测**生成完成之后**。生成环节绝不读市场价（走 `stripPrices`，见 CLAUDE.md 2026-06-11/19 决定）；预测时刻的市场隐含概率由 `scripts/world-cup/fetch-baseline-prices.ts` 一次性抓取留档，评测时才拿来当对照系。**所以"赢过市场"这个指标本身不违反盲测——它是给盲测预测打分，不参与生成。**

| 指标 | 定义（人话） | 取数字段 / 公式 | 目标值 |
| --- | --- | --- | --- |
| **Brier 技巧分** `bssPct` | 我们的预测比"直接抄市场价"准多少。>0 = 赢市场，<0 = 还不如抄市场 | `1 − Brier(ours)/Brier(market)`，`performance.ts:170`；Brier 见 `brier()` `:81` | **北极星：> 0（赢市场）**；及格线 ≥ 0 |
| **ECE（校准误差）** `ecePct` | 把预测按 10 个概率档分箱，每箱"我说的概率"和"实际命中率"的差，按样本量加权平均 | 十分位可靠性，`performance.ts:148-159`，输出 `PerfBin{predPct, obsPct, n}` | **≤ 10pp**；理想 ≤ 5pp |
| **可靠性曲线** | 给人看的校准图：横轴=预测概率，纵轴=实际命中率，越贴 45° 线越好 | `Performance.bins[]`（每箱 `predPct` vs `obsPct`），已在 `/world-cup/performance` 渲染 | 目视贴近对角线，无系统性偏上/偏下 |

**注意事项（PM 必读）**：
1. **Brier 是"越低越好"的损失，技巧分是"越高越好"的相对分**——别看反了。`bssPct` 这个相对口径才是对外能说的"相对市场水平"。
2. **ECE 需要足够样本才有意义**。世界杯批次有 `settled` 场已结算样本（`PerfAgg.settled`）；C 端单个用户的问题往往是一次性、无结算的（"2026 年前美伊达成核协议吗"要等到截止日才知道对错）。**C 端校准只能在"有明确结算 + 累积足够多 run"的题目上算，短期靠世界杯这类可结算批次背书，不要假装单个 C 端 run 能算 ECE。**
3. **置信区间也要校准**：结论卡给的是 80% 主观可信区间（Bayesian，非频率派）。要单独追踪"标称 80% 的区间，事后真的盖住结果约 80% 的次数吗"（覆盖率 coverage）。这是 `confidenceInterval:[lo,hi]` 字段的事后核对，目前 `performance.ts` 还没算，列为待补指标。

### 12.2 最佳预测命中 —— 方向对不对

**这一节回答的问题**：撇开精确概率，我们押注的那个结果（概率最高的 outcome），最后真发生了吗？这是给非技术用户看的"最直白的准不准"。

| 指标 | 定义 | 取数字段 | 目标值 |
| --- | --- | --- | --- |
| **最佳预测命中率** `bestPickPct` | 我们概率最高的那个 outcome = 实际结果的占比 | `bpHit / settled`，`performance.ts:165`；选最高 outcome 逻辑 `:108` | 显著高于随机基线 |
| 命中计数 | 命中场数 / 已结算场数 | `bestPickHit` / `settled`，`PerfAgg` | 作为绝对量参考 |

**注意事项**：
- **随机基线要按题目结构算**，不能一刀切 50%。三选一（主胜/平/客胜）随机基线约 33%，二元题约 50%。所以"命中率 60%"在三选一题里很强、在二元题里平庸。报告里必须**同时标注题目类型和对应随机基线**，否则数字会骗人。
- 最佳预测命中和 Brier 技巧分**会打架**：可能方向全对（命中率高）但概率给得太极端（Brier 差）。两个都要看，命中率是"面子"，Brier/ECE 是"里子"。

### 12.3 参与 / 留存 —— "活报告"这套交互有没有人用

**这一节回答的问题**：12-15 分钟的长任务，用户愿不愿意等完？"边长边对话"的设计，有没有让人真的去插话、去追问、去回来看？这是判断 §3-§5 那套交互投入值不值的核心证据。

**取数来源**：现有 `predictionUsageEvents` 表（`packages/db`）已经记 `status: running|complete|failed` + `startedAt/completedAt`。异步化（§5）后新增的 `ResearchReport.contextLog[]` / `followups[]` / `costActual` 字段是参与度细粒度数据的来源。

| 指标 | 定义 | 取数字段 / 来源 | 目标值（建议，待拍板） |
| --- | --- | --- | --- |
| **完成率** | run 跑到 `run.complete` 的占比（vs 中途 abort / 超时 failed） | `predictionUsageEvents.status='complete'` / 总数 | ≥ 75% |
| **中途放弃率（护栏）** | 用户在 run 跑完前关页面/离开 | 客户端断流事件 vs `status='running'` 未收尾的（注意 §HIGH-3：异步后收尾必须后台 worker 写，否则 `running` 泄漏会污染此指标） | < 25% |
| **插话采纳率** | 发生 ≥1 次"加 context"且被采纳的 run 占比 | `contextLog[].length > 0` 的 run 占比；采纳由 `context.applied` 事件确认 | 验证用，无硬目标 |
| **追问深度** | 每个父 run 平均衍生几个 followup 子 run | `followups[].length` 均值 | 越高越说明"可对话"成立 |
| **回访率** | 用户离开后回来看快照/历史的占比 | `GET /runs/{id}` 快照命中 + 历史列表点击 | 异步化后才有意义 |
| **周活完成 ≥1 次（北极星）** | WAU 中至少完成一次完整 run 的人数 | `predictionUsageEvents` 按 `userId` + UTC 周聚合 | 随放量定基线 |

**注意事项**：
1. **现在量不出来**：当前 C 端三条 driver 里 mock 12 秒跑完、VPS 120s 超时、api 只叠旁白（见可行性修正 CRITICAL-2），**还没有真正的 12-15 分钟长 run 接进 C 端**。所以"中途放弃率""完成率"这些长任务体感指标，**要等真长 run 接进来 + 异步化落地后才有数据**，Phase 0/1 阶段先埋点、不强求达标。
2. **`disabled` 模式（无 `DATABASE_URL`）不写 `predictionUsageEvents`**（`consumePredictionRunQuota:259` 直接放行）。本地/演示态下这些指标全是空的——**指标采集明确要求生产配 `DATABASE_URL`**。

### 12.4 决策采纳 —— 用户看完后，真的拿它做决定了吗

**这一节回答的问题**：预测准、好看都不够。最终要看用户**看完报告后有没有改变行为**——这是产品"有用"的硬证据。这也是"活报告 + 可交互台账"区别于一张静态报告的价值兑现点。

| 指标 | 定义 | 取数来源 | 目标值 |
| --- | --- | --- | --- |
| **决策采纳率（北极星）** | 用户在报告内产生**实质交互**的占比：忽略/调权某条证据、展开节点看 rationale、点开来源原文、发起追问 | 前端交互埋点（§6 第一层：`EvidenceLedger` 忽略/降权、节点 `expanded`、url 点击）；后端 `contextLog` / `followups` | ≥ 40% run 有 ≥1 次实质交互 |
| **结论被引用/导出** | 报告被分享、导出、或结论被复制 | `GET /runs/{id}` 分享链接命中 + 导出动作埋点 | 验证用 |
| **"忽略证据→重算"使用率** | MVP 主卖点：用户用了"忽略此条即时重算"功能的占比 | 前端即时重算触发计数（秒级、0 token，见 §6 第一层） | ≥ 20% run 触发过 |
| **误导率（护栏，最重要）** | 标"高置信"的结论，事后被证明方向错误的占比 | 高置信 run 的 `bestPick` vs 实际结果（需结算）；对照 `conclusion.verdict` | **趋近 0；任何一例都要复盘** |

**注意事项**：
1. **采纳率不等于"采纳了正确决策"**。用户可能被一份错报告说服去行动——所以**采纳率必须和误导率/校准一起看**。一个采纳率高但误导率也高的产品，是在高效地把人带沟里。这是本产品最需要警惕的失败模式。
2. **真钱交易闸门**：本仓是真钱实盘项目（CLAUDE.md 顶部警告）。C 端"决策采纳"指的是**用户自己的认知/行为改变**，**绝不包含**用 C 端预测直接驱动下单——下单依据必须出自带归档的 `forecast:*` 流程（`recommendation.json`），C 端报告在交易语境里只能是参考、必须标"非交易依据"。这条是政策红线，不是指标口径。

### 12.5 成本 / 单次 —— 一次预测花多少，划不划算

**这一节回答的问题**：一次完整 run 烧多少 token、占多少墙钟、调几次外部接口？追问/加 context 的增量成本是多少？这决定了配额模型和定价能不能成立。

**实测基线（来自 `docs/diagrams/forecasting-cost-profile.md`，2026-06-10 实跑，以实测为准不靠传闻）**：

| 维度 | 单次完整 run 基线 | 备注 |
| --- | --- | --- |
| 墙钟 | **12-15 分钟**（719-750s 实测） | 渲染占 95%；静默 5 分钟内属正常 |
| 输入 token | **~40-50k / 轮** | |
| 输出 token | **~5k / 轮** | |

| LLM 调用 | 1（报告渲染）+ 可选 1（验证） | |

| 指标 | 定义 | 取数字段 / 来源 | 目标值 |
| --- | --- | --- | --- |
| **单次完整成本（北极星）** | 一次 run 的 token + 墙钟 + 外部调用 | 新增 `ResearchReport.costActual{elapsedMs, inputTokens, outputTokens, externalCalls, llmCalls}`，写入 `runtime-artifacts/pulse-live-cost-ledger/` | 持平或随缓存优化下降 |
| **增量重算成本** | 追问/加 context 相对从头跑省了多少 | 分级：忽略证据=**0 LLM**（纯前端计算）；加 note=约 1 次便宜 LLM；whatif=父 run 证据池上只重算条件树 | 远低于完整 run |
| **缓存命中率** | 整 run / 证据池 / prompt 三层缓存命中占比 | 整 run 按 `hashText(eventText+tier+locale+marketPrice)` 命中（mock 已用）；证据池按 query+日期窗口 | 越高越省 |

**注意事项**：
1. **心跳不掩盖慢引擎**：§4 的心跳（每 10-15s 一帧）只改善"静默像死机"的体感，**不是给慢引擎打掩护**——渲染 > 15 分钟仍按 regression 处理，这是硬约定。
2. **tier 策略影响成本**：首次生成可上 `skuld`（旗舰、贵），追问/加 context 默认降到 `verdandi/urd` 控成本（§9）。成本指标要**按 tier 分桶**，否则均值会被旗舰拉偏。
3. **配额单位与成本挂钩（待拍板）**：现按"每 run"计（日 5 / 月 50 / 并发 1，env `PREDICTION_DAILY_RUN_LIMIT` 等）。对话式产品追问频繁，会被两次对话耗尽配额——计费单位重定义（按会话？整轮 vs 局部重跑分级？）是产品策略，需用户拍板，agent 不擅自定。

## 13. 里程碑与范围切分

> 本章把"活报告控制台"切成 **MVP → v1 → v2** 三段，外加一个零风险的前置预热段（Phase 0）。每段都给出：**这段要交付什么、做完怎么验收、哪些事明确不在这段做**。验收标准一律写成"可观测、可测量"的具体动作，不接受"ready / done"这种含糊词。

### 13.0 切分总览（给 PM 的一页结论）

**先说三句最重要的结论：**

1. **依赖顺序被纠正过**：统一蓝图原本把"心跳 → 纯前端交互 → 异步化"排在前面，这个顺序是错的。真实情况是 **异步化（异步 run + 可重连流 + 落库）是几乎一切的前置**——加 context、刷新恢复、历史、甚至"长任务里发心跳"都依赖它。原因：当前生产部署是 Vercel Serverless（`vercel.json` 用 `@vercel/next`、未配 `maxDuration`），单函数有墙钟硬上限，**现有 12–15 分钟的真 run 在 Vercel 上根本跑不完**，连"每 10–15 秒发一帧心跳"都会在函数被回收时断掉。所以 MVP 必须先解决"长任务承载在哪"。

2. **MVP 不追求"真模型数字"**：当前 `/research` 三条 driver 里，mock 走 `replayRun` 12–14 秒跑完，api driver 只把模型文本当旁白叠在 demo 骨架上（`api-driver.ts` 的 `TODO(integration)`），数字仍是 `buildPredictionDemoRun` 生成的。**让数字变真**是 v1/v2 的引擎侧工程，不塞进 MVP。MVP 的交互（忽略某条证据→秒级重算）作用在 demo 数字上，必须诚实标注这一层。

3. **盲测边界全程是硬闸**：每一段验收都包含"含市场价的 context 在生成路径被拒绝"这条校验（2026-06-11 / 06-19 用户决定）。这不是某一段的特性，是贯穿三段的不可退让约束。

**一张表看清切分：**

| 段 | 代号 | 一句话目标 | 核心可观测交付 | 主要风险 / 是否需用户拍板 |
| --- | --- | --- | --- | --- |
| Phase 0 | 预热 | 长任务不再像死机 | 心跳事件 + 活报告骨架（从第 10 秒铺出来） | 低风险，纯前端 + 一个新事件类型；**不需拍板** |
| **MVP** | v0.1 | 长任务真正能跑、断网能回、能加料 | 异步 run + 可重连流 + 落库 + 旁路 POST 加 context（阶段边界采纳，仅 mock 链可演示真生效） | **需拍板**：承载进程放哪（Serverless 不行）、配额计费单位 |
| **v1** | v0.5 | 报告从只读变可对话，数字开始变真 | 纯前端即时交互层全量 + api-driver 数字落地（zod 校验）+ followup 子 run | 中风险：结构化推理 prompt + schema + 失败回退 |
| **v2** | v1.0 | 真节点级局部重算 + 历史/版本对比 | 阶段类型化后的真·局部重跑 + 版本对比 + 跨 repo 契约统一 | 高风险：触及引擎重构与 raven-cloud 跨 repo 迁移 |

### 13.1 Phase 0 · 预热段（长任务不再像死机）

**为什么先做这段**：它零依赖、低风险、1–2 天能上，且能立刻改善体感。但要诚实——它**只改善体感，不解决长任务能否跑完**（那是 MVP 的事）。

**交付物：**

- `events.ts` 新增两类事件：`run.heartbeat { seq, ts, stageId?, elapsedMs?, etaRangeSec?:[min,max] }` 与（可选）`stage.heartbeat`。`state-machine.ts` 加对应 `case`——注意现有 reducer 的 `default` 分支天然吞未知事件（已验证），所以老 driver 不受影响。
- `replay.ts` 在 stage 之间穿插发心跳帧（每 10–15 秒一帧）。
- UI 新增"仍在工作"指示器：显示"当前在干嘛 + 已耗时 + 该阶段预计区间"，数据源就是心跳帧。
- 活报告骨架：右栏从第 10 秒铺出 7 阶段 + A/B/C 节点 + 来源区空位（灰显），内容顺着事件一格格"长"进去，而不是跑完一次性弹出。

**验收标准（可测量）：**

- [ ] 在 mock 链跑一次，全程能看到心跳帧（用浏览器 Network 面板确认 `run.heartbeat` 帧间隔 ≤ 15 秒）。
- [ ] 右栏骨架在 `phase==='running'` 阶段即可见，不再只在 `phase==='complete'` 渲染（截图对比 before/after）。
- [ ] `state-machine.test.ts` 补：喂入 heartbeat 事件后状态正确更新、且喂入未知事件时状态不崩（向后兼容回归）。
- [ ] **apps/web 三件套**：i18n 三语（en / zh-CN / zh-TW）补齐心跳与骨架文案；桌面 + 移动双视口截图自评（布局不崩、无 console error）；本地 `pnpm --filter @autopoly/web build` 通过。

**明确不做：**

- 不在这段接真 12–15 分钟 run（接了也会撞 Serverless 墙钟，见 MVP）。心跳此刻只在 mock 的 12 秒里跳几下——它的真正价值要等 MVP 把长 run 接进来才兑现。
- 诚实底线：渲染持续 > 15 分钟仍按 **regression** 处理（对齐 `docs/diagrams/forecasting-cost-profile.md` 约定），心跳不得用来给慢引擎打掩护。

### 13.2 MVP · v0.1（长任务真正能跑、断网能回、能加料）

**这是工程量最大、也最关键的一段**。一句话：把"整条流挂在一个 POST 上"拆成"异步 run + 可重连流 + 落库"，顺带补上"加 context"的反向通道。

#### 前置阻塞决策（开工前必须拍板）

| 待拍板项 | 为什么是阻塞项 | 建议默认 |
| --- | --- | --- |
| **长任务承载进程放哪** | Serverless 单函数跑不满 12–15 分钟，且实例无状态——POST 创建的 run 和 GET 订阅的流几乎一定落在不同实例，进程内 store 必然投递错实例。**"apps/web 进程内"这一档在 Serverless 上不可用，不是 tradeoff** | 长任务搬到常驻进程（raven-cloud / VPS orchestrator），apps/web 只做 Serverless 代理 + 读 DB 快照 |
| **配额计费单位** | 现按"每 run"计（日 5 / 月 50 / 并发 1，见 `prediction-access.ts`）。对话式产品追问频繁，两次对话就耗尽——属产品策略，agent 不擅自定 | 待用户定；建议"整轮生成"与"局部重算/追问"分级计费 |

#### 交付物

**1. 异步化 API 表面（扩展自现有单一 `/api/research/stream`）：**

### 14.1 可行性风险

#### 14.1.1 🔴 CRITICAL — 部署形态：Serverless 挂不住 12–15 分钟长连接

**现在的问题。** 蓝图假设"现在整条流挂在一个 POST 的生命周期上"是个可保留的同步长流。但生产部署是 **Vercel Serverless**（`route.ts:20` 用 `runtime="nodejs"`，`vercel.json` 无 `maxDuration`，CLAUDE.md 明确"合入 main 触发 GitHub→Vercel 自动部署"）。Serverless 函数：(a) 墙钟有硬上限（Pro 默认 60s，未配置 `maxDuration`），现有 12–15 分钟 live run **在 Vercel 上根本跑不完**——今天能跑完的只有 mock（约 12–14s）和本地 Node；(b) 实例无状态、跨调用不共享内存，POST 创建 run 与 GET 订阅流**几乎一定落在不同实例**，进程内 store 必然投递到错误实例。

**会影响什么。** 蓝图把"异步化"定位成"主要工程但有现成地基"，并建议"先在 apps/web 出可用版再迁 raven-cloud"。在 Serverless 上这条路**走不通**——apps/web 进程内 run 注册表不是一个 tradeoff 选项，而是根本不可用。连"心跳每 10–15 秒一帧"都受墙钟限制：函数 60s 被杀，心跳发不到第 5 帧。

**建议动作。**
- 把"承载位置"从"待拍板的两个选项"升级为**前置阻塞决策**，并明确排除"apps/web 进程内"这一档。可行的两条路：(1) 长任务搬到**常驻进程**（raven-cloud / VPS orchestrator），apps/web 只做 Serverless 代理 + 读 DB 快照；(2) 用 **Vercel 支持的 background/queue**（外部 worker + DB/Redis 轮询）。
- run 状态、事件序列、`seq` 必须落 **Postgres / Redis**。已有 `packages/db`（Postgres），但**无 runs 表**——这是新建 migration，不是复用。可重连流读 DB 回放，而非读内存。

#### 14.1.2 🔴 CRITICAL — Phase 顺序前后倒置，会导致返工

**现在的问题。** 蓝图的阶段序是 `Phase 0 心跳 → Phase 1 纯前端交互 → Phase 2 异步化 → …`。这个顺序错了：**异步化是其他一切的前置**（加 context、刷新恢复、历史、心跳都依赖它）。在 Serverless 上先做 Phase 0/1，会在 Phase 2 撞墙时被推翻重做。

**建议的正确依赖序：**

| 阶段 | 内容 | 阻塞依赖 |
| --- | --- | --- |
| Phase A（前置拍板） | 定承载进程（排除 Serverless 进程内）+ 建 `runs` 持久化表 | 用户拍板 14.4.1 |
| Phase B | 异步 run + DB 回放续传 + 配额收尾改后台写 | A |
| Phase C | 心跳 + 左流右文档双栏 UI + 纯前端交互层（忽略来源即时重算 / 节点展开 / url 可点） | B（心跳价值依赖真 run 接入） |
| Phase D | 反向通道（加 context + 阶段边界采纳，MVP 仅 mock 链可演示） | B、C |
| Phase E | api-driver 数字变真 + 真引擎局部重算 / followup 子 run | D |

每阶段验收必须是可测标准（非 "ready/done"），且过 `apps/web` 三件套闸门：i18n 三语（`en` / `zh-CN` / `zh-TW`）、桌面+移动双视口自评、本地 `pnpm --filter @autopoly/web build` 通过（用 `build` 不用 `exec next build`）。

#### 14.1.3 🟠 HIGH — C-end 还没有真正的长 run，心跳在为尚不存在的问题做方案

**现在的问题。** 三条 C-end driver 没有一条现在会让用户等 12–15 分钟：`vps-agent-driver.ts:53` 默认 120s 超时；`api-driver.ts` live 路径只把模型文本当旁白（`splitNarration` 砍到 8 行）叠在 `buildPredictionDemoRun` 生成的 demo 骨架上，数字仍是 demo 的；mock 走 `replayRun` 12–14s 走完。那条 12–15 分钟 / 渲染占 95% / 静默 5 分钟正常的画像，来自 `scripts/pulse-live.ts` 与 orchestrator CLI（见 `docs/diagrams/forecasting-cost-profile.md`），**不是 `/research` 控制台的**。

**会影响什么。** 先上心跳，但真 run 接不进来，心跳只在 mock 的 12 秒里跳几下，验收时看不出价值；等真接上 VPS 长 run，又会撞 14.1.1 的墙。

**建议动作。** 先回答 14.4.2（C-end 要不要跑真 12–15 分钟 run）。要 → 先解决承载 + 把 VPS 超时从 120s 提到 ≥18min 且改成可重连（Serverless 代理段仍受墙钟限制，所以代理段不能 hold 整条 SSE）。心跳本身 1–2 天没错，但其价值**依赖长 run 真接进来**，phasing 里要标这个依赖，不当独立卖点。诚实底线保留：心跳不掩盖慢引擎，渲染 >15min 仍按 regression 处理（不放宽容忍度）。

#### 14.1.4 🟠 HIGH — "阶段边界采纳"假设引擎是可被外部读取的协作进程

**现在的问题。** `replay.ts` 的 `replayRun` 是单向自驱动 async 循环（`for...of orderedStages` 一路 emit，中间只有 `sleep` 和只能 abort 的 `signal`），没有"阶段边界回头读队列"的挂钩。VPS driver 要么直通上游 SSE、要么本地 replay JSON，也没有这个挂钩。真引擎（orchestrator `daily-pulse-core` / `full-pulse`）是 CLI 批处理一次性产出 `pulse.json`；raven-cloud 的 `pulse-command` runner 更是 `spawn` shell 等退出——纯黑盒，**无阶段边界可注入**。

**建议动作。**
- mock/replay 路径上"阶段边界采纳"可做（循环里加 `await drainContextQueue(stageId)` 检查点）——这部分可行，作为 MVP 演示。
- 真引擎链上"运行中采纳 context"需把 orchestrator 改成可中断、阶段间可回灌输入的有状态服务——这是引擎重写，不在"不重写引擎"承诺内。**MVP 诚实口径：运行中加 context 真生效仅在 mock 链可演示；真引擎链短期只做"运行后 followup 子 run"**（followup 是新建 run、不要求中断旧 run，相对现实）。

#### 14.1.5 🟡 MEDIUM — "左流右文档"是全新 UI，不是"零到极少改动"

**现在的问题。** `research-console.tsx` 当前是单列纵向、composer 在下、跑完才出结果卡（结果卡仅 `phase==='complete'` 渲染）。改成"左活动流 + 右常驻活报告（第 10 秒铺骨架）"是布局重构 + 结果卡从 complete-only 改成 streaming-growing，外加常驻插话框、乐观回显气泡、可展开节点（要给 `ResearchStageState` / model 加 `expanded` 位）。叶子组件（`ConfidenceBar` / `UpdateWaterfall` / `EvidenceLedger` 的 SVG 绘制 + reducer + format/i18n）可复用，但**容器、双栏布局、渲染时机、交互层全是新写**。"80–90% 零改动"偏乐观。

**建议动作。** 复用范围限定到纯展示叶子组件；外壳 / 双栏 / 常驻文档 / 可交互层明确列为新建。双栏在移动端的坍缩是新的设计工作，纳入三件套移动自评。

#### 14.1.6 🟡 MEDIUM — SSE `id:` 续传与现有解析器不兼容

**现在的问题。** `events.ts` 的 `encodeResearchEvent` 输出 `event:<type>\ndata:<json>\n\n`，**无 id 行**；客户端 `use-research-stream.ts` 只认 `data:` 开头、忽略 `event:` 行，且用 `fetch + ReadableStream` 手动分帧，**不是原生 `EventSource`**——所以 SSE 标准的 `Last-Event-ID` 自动续传**根本不会触发**（那是 `EventSource` 的能力）。要续传必须：改 encode 加 `id:`、客户端记录 last seq、重连手动带 `Last-Event-ID` header、服务端按 seq 补发。reducer 本身确实几乎零改（`default` 分支吞未知事件，已验证 `state-machine.ts`）。

**建议动作。** 明确续传 = 扩传输层，不是"加个序号"。两条路：迁到 `EventSource` + GET（但 `EventSource` 不支持 POST body，需把 eventText 放 query 或先 POST 拿 runId 再 GET），或保持 fetch 流自己实现 `Last-Event-ID` 往返。别让"reducer 几乎零改"这句掩盖传输层重写。

#### 14.1.7 蓝图判断正确、可直接保留的部分（避免过度否定）

- reducer `default` 分支向后兼容老 driver —— ✅ 已验证（`state-machine.ts`）。
- 不上 WebSocket、用旁路 POST —— ✅ 方向对，与现有 SSE 协议不冲突。
- 盲测双闸（web zod + 引擎 guard，含市场价的 context 拒绝进生成）—— ✅ 符合 2026-06-11 / 06-19 用户决定。
- `PredictionEvidence` 四元组（`stance` / `weightPct` / `reliability` / `node`）作为可审计最小单元 —— ✅ 与 `prediction-engine-demo.ts` 实际 schema 一致。
- 成本画像（12–15min / 40–50k in / 5k out / 渲染 95%）—— ✅ 与 `forecasting-cost-profile.md` 一致。

### 14.2 成本风险

#### 14.2.1 🟠 HIGH — 配额计数机制在异步化后会泄漏

**现在的问题。** `prediction-access.ts` 的并发限制靠 `predictionUsageEvents.status='running'` 行计数，靠 `completePredictionUsageEvent` 收尾（现在写在请求 `finally` 里，依赖 HTTP 请求生命周期）。异步化后请求秒回、run 在后台跑、用户断开连接 → **没有任何地方保证 `complete` 被写回** → `running` 计数只增不减 → `concurrentLimit=1` 的用户**第二次永远被 429**。叠加：无 `DATABASE_URL`（disabled 模式）时 `consumePredictionRunQuota` 直接返回 `{allowed:true}` 不写 `predictionUsageEvents`，本地 / 演示态下配额 + 历史 + 共享 store 全空。

**建议动作。**
- 异步 run 的状态收尾**必须由后台 worker 写 DB**，不能依赖 HTTP `finally`；建议加 run 状态机 + 超时清扫（stale `running` 超过 N 分钟自动置 `failed`）。
- 明确"无 `DATABASE_URL` = 无持久化"：历史 / 共享 store / 分享在演示态必须降级或显式要求配 `DATABASE_URL`，不能假装有地基。

#### 14.2.2 🟡 MEDIUM — 局部重算的"几分钟精修"未实测，不能直接承诺

**现在的问题。** 蓝图把"加新料→重跑受影响节点"当卖点，但底层引擎 `pulse` 单次报告渲染是 **1200s 单一超时、无中间状态恢复、无分批**（见 orchestrator `stage-flow` 与成本画像）。stage 4–6（证据加权 / 结构模型 / 贝叶斯）当前是自由 Markdown 文本而非类型化对象，做不到真正的节点级局部重算。

**建议动作。** 分级诚实落地：
- **忽略 / 降权 / 提权某条证据** = 纯前端计算、0 LLM、秒级 —— 作为 MVP 可交互主卖点（能精确做）。
- **加新料重算** = 短期用"重跑受影响阶段"近似 + 诚实标注等待；待 stage-flow 阶段类型化后再做真节点级。
- **followup 追问** = 继承父 run 证据池的子 run，只算条件树，默认 tier 降到 `verdandi` / `urd` 控成本（首次生成才上 `skuld`）。

#### 14.2.3 🟡 MEDIUM — 真实数字打通是引擎侧最大工作量，不是"一笔"

**现在的问题。** 蓝图同时说 api-driver 的 INTEGRATION POINT 是"数字变真的关键一笔"，又在别处承认"stage 4–6 自由文本→类型化对象是引擎侧最大真实工作量"——两句自相矛盾。`api-driver.ts` 的 `TODO(integration)` 实际要做：让模型严格按 schema 输出条件树 + 证据四元组 + 贝叶斯链、zod 校验、失败重试 / 降级，且保证盲测不读市场价。这是整套结构化推理 prompt + 输出契约 + 校验 + 回退，不是"一笔"。

**建议动作。** 统一口径，定为独立中等工程项。明确：在它打通前，"局部重算 / 加新料重算"都建立在 demo 骨架上——"忽略某条证据→秒级 0-token 重算"只能重算 demo 数字。MVP 卖点必须诚实标注这层。

#### 14.2.4 成本控制保留项（蓝图正确部分）

三层缓存（整 run hash 命中回放 / 证据池按 query+日期窗口缓存 / prompt caching）、增量重算分级、tier 策略均与现有实测一致，保留。约定：每次 live run CSV 追加进 `runtime-artifacts/pulse-live-cost-ledger/`。

### 14.3 可信 / 合规风险

#### 14.3.1 🔴 CRITICAL（政策红线）— 盲测边界必须双闸强制

**约束。** 项目硬约束（2026-06-11 / 06-19 用户决定）：预测的*生成*环节任何时候不得读取市场价格 / 隐含概率（走 `stripPrices`）。用户在反向通道贴的 context 若含市场价，**生成路径必须拒绝**，只允许进事后对比（`/world-cup/performance` 那类基准评测）。

**实现要求。** zod schema + 服务端 guard 双闸：(1) web 校验层在 `POST /runs/{id}/context` 入口拒绝含市场价 / 隐含概率的注入进入生成路径；(2) 引擎层 guard 兜底（即便 web 漏了，引擎也不读）。任何放宽都属政策变更，**必须停下等用户确认，agent 不得擅自调整**。

#### 14.3.2 🟠 HIGH — 用户提供的 context 不得冒充一手核查

用户注入的 context 一律标 `sourceType='用户提供'`、`reliability` 偏低、显式展示，绝不冒充一手核查结论。URL 抓取设白名单 + 超时；`note` 文本走注入检测（防恶意 prompt 当 context 喂进模型）。可追溯：每条 context 对哪个 stage / node 产生何影响记入 `contextLog`，成本记入 `costActual` → cost-ledger。

#### 14.3.3 🟠 HIGH — 跨 repo 契约漂移违反"禁双源不一致"硬约束

**现在的问题。** predict-raven 与 raven-cloud 两套 schema 已漂移，且是独立 repo / 独立类型 / 独立 store：

| 维度 | predict-raven | raven-cloud |
| --- | --- | --- |
| `stance` | `support / oppose / mixed / neutral` | `supports / weakens / mixed / context` |
| stage key | `definition / query-design / evidence / weighting / model / bayes / market` | `intent_definition … output_and_market_compare` |
| 持久化 | `packages/db`（Postgres，含 usage 表） | MemoryStore（重启即丢） |

"统一"意味着改 raven-cloud 的 types + runners + demo + store，以及任何已依赖旧 schema 的 raven-web，是跨 repo 破坏性变更，触及 CLAUDE.md"禁双源不一致"。

**建议动作。** 列为独立跨 repo 工作项，定迁移顺序：先 predict-raven 定契约（统一到 `PredictionEngineRun` 一套）→ raven-cloud 适配 + 双写期 → raven-web 跟随。不是塞一句"加个映射函数"。

#### 14.3.4 🟡 MEDIUM — 可访问性（用户视力受限）

节点展开 / SVG 图表（`ConfidenceBar` / `UpdateWaterfall`）/ 插话栏需补 `aria` + 键盘可达；**关键结论保证纯文本可读**（概率 + 区间 + verdict 不能只存在于 SVG 里）。纳入前端三件套自评。

#### 14.3.5 🟡 MEDIUM — 安全杂项

私钥 / env 路径不外泄（现报告里出现过 env 文件路径，注入回流时勿带出）；run 快照 / 分享接口须做用户归属鉴权（`predictionUsageEvents.userId` 已有归属，但 runs 表是新建，鉴权要从头设计）；反向通道 POST 须复用现有 `consumePredictionRunQuota` 的 401/403/429 路径，避免成为绕过配额的后门。

### 14.5 残余风险（已知但本期不解，需登记）

- **Serverless 代理段的墙钟**：即便长任务搬到常驻进程，apps/web 作为 Serverless 代理转发 SSE 时仍受墙钟限制——代理段不能 hold 整条流，必须靠"GET 独立可重连 + DB 回放"绕过。这是架构约束，非 bug。
- **真引擎阶段间不可中断**：14.1.4 的局部重算在引擎类型化（stage 4–6 升级为类型化对象）前无法真节点级，MVP 用近似 + 诚实等待反馈兜底。
- **多实例 store 一致性**：serverless 多实例下 run 级 store 必须 DB/Redis，否则反向通道注入投递到错误实例——已在 14.1.1 / 14.2.1 覆盖，落地时需压测验证。
- **成本画像样本量**：12–15min 基线来自 n=3 完整 run + 87 题世界杯批次，多周趋势未知；按约定每 session 追加 cost-ledger 持续校准。

| **心跳（heartbeat）** | 长任务里每 10–15 秒发一帧的轻量信号，带"当前在干嘛 + 已耗时 + 预计区间"。用途：把"静默 5 分钟（实测正常）"翻译成会动的"仍在工作"指示器，避免用户以为死机。**不是给慢引擎打掩护**——渲染 >15 分钟仍按 regression 处理。 | 新增 `run.heartbeat` / `stage.heartbeat` 事件 + reducer 加 case。 |
| **异步 run + 可重连流** | 把"整条 12–15 分钟流挂在一个 POST 上"拆成"POST 秒回 runId（任务异步跑）+ GET 独立订阅流（断网能重连）"。影响：解决长任务一断全丢，也是反向通道、刷新恢复、历史的共同前提。 | `POST /runs` → `GET /runs/{id}/stream`。**在 Vercel Serverless 上必须配常驻进程 + DB 落库，不能用进程内 store。** |
| **Last-Event-ID 续传** | SSE 标准的断线重连机制：每帧带递增序号 `id`，客户端重连时带上最后收到的 id，服务端只补发更大序号的事件，不重放整段。 | 现 `events.ts` 的 `encodeResearchEvent` **不发 `id:` 行**，客户端 `use-research-stream.ts` 用 `fetch`+`ReadableStream` 手动分帧（非原生 `EventSource`），续传需自己实现往返，不是"加个序号"。 |
| **局部重算（incremental recompute）** | 用户加料或改参数后，只重跑受影响的节点及下游，而不是整轮 12–15 分钟重来。分级：忽略某条证据=前端秒级 0 token；加新料=重跑受影响节点（需引擎配合，第二步）。 | 忽略来源=纯前端权重重算；加新料=SSE 带 scope 参数。 |
| **盲测边界（market-blind）** | 项目硬约束：预测的"生成"环节任何时候不得读取市场价格 / 隐含概率来形成预测。用户贴的 context 若含市场价，生成路径必须拒绝，只能进"事后与市场对比"环节。 | web zod 校验层 + 引擎层 guard 双闸；对照 `scripts/world-cup/` 的 `stripPrices`。用户决定见 2026-06-11 / 2026-06-19。 |
| **条件概率树 P(A)×P(B\|A)×P(C\|A,B)** | 把一个复杂预测拆成 2–3 个条件节点连乘：先估 A 发生的概率，再估 A 发生下 B 的概率，依此类推。右栏以可点开的树状卡片展示，每个节点带 rationale（为什么给这个数）。 | `result-charts.tsx` 的 `ConditionalTree`；数据来自 `PredictionModelNode[]`。 |
| **贝叶斯瀑布（Bayes waterfall）** | 一张台阶图，展示概率从基线（prior）出发、每吸收一条证据涨/跌一截、最终收敛到结论的全过程。让用户看到"数字是怎么一步步被证据推到这儿的"。 | `result-charts.tsx` 的 `UpdateWaterfall`；数据来自 `PredictionUpdate[]`（`label/from/to/explanation`）。 |
| **证据台账（Evidence Ledger）** | 按影响排序的证据表，每条带：立场色块、标题+日期+来源、影响 ±pp、信度 0–1、挂在哪个节点（A/B/C）。本产品把它从只读升级为可点开看原文、可"忽略此条"即时重算。 | `result-charts.tsx` 的 `EvidenceLedger`；数据来自 `PredictionEvidence[]`。 |
| **driver（mock / api / vps）** | 产生预测事件流的三条可热切换后端：mock=确定性 demo（做 UI/QA 与兜底）；api=直连 Anthropic/OpenAI；vps=转发到远端编排器（背后是真 pulse 引擎）。三者吐同一套事件，前端无需关心用了哪条。 | 由 `RESEARCH_DRIVER` 环境变量切换；注册表在 `drivers/index.ts`。 |
| **tier（Norns：urd / verdandi / skuld）** | 推理深度三档，控制模型大小与 token 预算。urd 轻、verdandi 默认均衡、skuld 旗舰。策略：首次生成可上 skuld，追问/加 context 默认降档控成本。 | 经 `@autopoly/norns` 别名层映射到具体模型。 |
| **followup（追问）** | 对已完成报告的针对性提问（如"为什么 B 节点只给 0.15""换个截止日会怎样"）。生成一个继承父 run 证据池的子 run，只重算相关部分，不重跑整管线、省 token。 | 新增 `POST /runs/{id}/followup`，返回针对性补充流。 |
| **乐观回显（optimistic echo）** | 用户插话后，界面立刻显示一条"你说了…"气泡（不等后端确认），收到 `context.applied` 后再变成"已在[称重]阶段采纳"。给即时掌控感，同时诚实标注真正生效的时点。 | 前端本地状态先行，`context.applied` 事件到达后切换文案。 |
| **stripPrices** | 盲测的实际执行点：预测管线只用市场数据做事件结构与结算映射，主动剥掉价格字段，确保模型看不到市场隐含概率。 | `scripts/world-cup/` 下的预处理步骤；事后基准评测（`/world-cup/performance`）才允许重新引入价格。 |
